## 裁决结果（2026-09-05；Q1 于 2026-09-06 修订）

10 项均按本文档推荐结论采纳，其中三项带增补：Q7 按 P1-7 增补"文件名弱校验 + 强警告二次确认"；Q8 判定规则采纳、".bin 内嵌版本解析"留 M3 核对；**Q1 修订（2026-09-06，用户裁决"每种设备都有自己的参数设置功能"）：基础参数配置 UI 提前进 v1 主线（不再置于 M8）**，三家族配置表单已在原型 v2.1 完整设计；控制类命令（电源/校准/任务/时间同步 UI）与 0xF9 仍延后。需求第 14 章闭合，需求版本 v0.6。

## 逐项裁决建议

### 1. 参数配置 UI 是否进入 v1

**推荐结论**：基础参数配置进入 v1，但排在 M8「UI 完整化」批次，按设备逐个开放（建议顺序：UDS100 → DC200Family → SVC100）；OTA 主线（M4–M7）不受阻塞。电源开关（`0xFE`）、校准（`0xFD`）、时间同步（`0x06`）、SVC100 任务（`0x03/0x04/0x05`）、SVC100 直接阀控（`0xF9`）不进入 v1 主 UI，协议层照常建模。

**依据**：
- 需求第 6.2 节要求协议层必须实现全部命令，与 UI 开放解耦；
- 需求第 11 章处置表将各类配置标为「协议层必须；UI 待定」，里程碑 M8 定义为"根据最终 v1 矩阵补齐配置"；
- 固件证据齐备：UDS100 配置载荷 9 字节、DC200Family 4 字节、SVC100 8 字节（`fromBleDataHandle()` cmd `0x02`，见 firmware-traceability.md §4.2–4.4），边界值已明确，可直接生成测试向量；
- 现场工具的核心价值包含配置；若 v1 完全不开放配置，iOS 版只能作"升级器"使用，替换性不足。

**影响**：
- 采纳：M8 增加 3 个设备配置表单（P-05）、输入边界校验（UDS100 阈值 `30-4500 mm`、周期 `1-1440`、GPS `0/10-1440` 等）、固件接受/拒绝边界向量；约 1–2 周人时。
- 不采纳（配置完全不进 v1）：节省上述工作量，但需在需求中记录为 iOS 受限行为，现场配置继续依赖 Android。
- 无论是否采纳，上报周期为 `0` 的固件行为（DC200Family/SVC100 接受 `0`）需产品裁决开放或隐藏，与需求 7.4 一致。

**决策人**：产品 + 研发。闭合时点：M0。

### 2. 状态展示字段范围

**推荐结论**：按 `DeviceRegistry` 能力表完整展示 Android 状态页全部字段（UDS100 17 项、DC200Family 11 项、SVC100 15 项，需求 7.1–7.3），v1 一律只读。

**依据**：
- 协议解析层必须支持全部 TLV 类型（firmware-traceability.md §4.2–4.4 已登记 0x01/0x03/0x09/0x0A/…/0xFF），"只展示版本+电量"并不能减少协议层工作量，只是放弃已建模数据的视图；
- 需求 UI 验收标准 3 要求"四类设备的差异能力在 UI 上可识别、可解释"，完整字段正是差异能力的体现。

**影响**：
- 需要 FieldRow 状态组件 + 三套设备状态模板（P-03）；
- 字段单位与格式（温度符号、经纬度小数位、电压 mV/V）需要 FW-VEC 向量逐项确认，列入 M3 测试基线；
- 无新增协议工作。

**决策人**：产品。闭合时点：M0（与 UI 设计基线 M1 联动）。

### 3. Debug 原始命令入口是否进入 v1

**推荐结论**：进入 v1，作为隐藏内部入口：设置页连续点击版本号 7 次开启（对齐 Android 常见做法），`dev` 构建默认开启；不做首页入口。

**依据**：
- 需求 9.1 明确该能力"对现场协议排查和 OTA 联调非常重要"；第 11 章处置表要求"架构保留"；
- OTA 真机联调（M6/M7）阶段本身就需要原始收发手段定位问题。

**影响**：
- 新增 P-06 Debug 页：原始 hex 发送、原始 Indicate 展示、收发时间戳日志；发送前二次确认防误触；
- 架构上 Session 层需暴露 rawWrite/rawIndicate 旁路（已在大纲 §7 预留），不改 CoreBluetooth Adapter。

**决策人**：产品 + 研发。闭合时点：M0。

### 4. 手工 DevEUI 与二维码入口是否进入 v1

**推荐结论**：v1 主 UI 不开放；架构保留 `TargetedScan` 能力（扫描过滤器支持目标后缀匹配），UI 放置禁用占位。开放前置条件：M3 阶段必须先从固件广播源码核对 DevEUI 在广播包（AD 结构）中的确切位置与格式，形成 FW-REF 后才允许实现。

**依据**：
- Android 的 DevEUI 匹配建立在扫描记录解析之上；iOS 端 CoreBluetooth 拿到的广播数据结构不同，不能照抄 Android 规则，必须回到固件广播包定义；
- v1 主线是 OTA，目标定位属于效率增强，不阻塞验收矩阵 A-01–A-10。

**影响**：
- v1 无实现成本；
- 后续开放需要：AVFoundation 扫码 UI、DevEUI 解析、广播原始数据解析与固件证据；已在大纲 §6 FeatureSurface 预留 `targetedScan`/`barcodeScan` 开关。

**决策人**：产品。闭合时点：M0（结论即"不进 v1"）。

### 5. 最低支持 iOS 版本

**推荐结论**：iOS 17.0。

**依据**：
- 项目 2026 年启动、面向内部工程团队，iOS 17+ 已覆盖绝大多数在役 iPhone；
- iOS 17 的 Observation（`@Observable`）直接满足需求 3.4 硬性要求 3/10（BLE 回调不直改 UI、状态经快照同步），显著减少样板代码；
- Swift Concurrency（actor/AsyncStream）在 iOS 17 上行为成熟稳定；CoreBluetooth API 在 16/17 无差异；
- 若必须兼容 iOS 16，ViewModel 层需退回 `ObservableObject`/Combine，增加出错面与测试矩阵。

**影响**：
- 采纳：放弃 iPhone 8/X 等无法升级 iOS 17 的机型（需在需求中记录）；
- 不采纳（iOS 16 基线）：架构大纲 §9 的状态同步方案改为 ObservableObject，其余分层不变，增加约兼容工作量。

**决策人**：产品 + 研发。闭合时点：M0（工程创建前必须定案）。

### 6. 最低支持 iPhone 机型

**推荐结论**：跟随 iOS 17 官方支持下限，即 iPhone XS/XR（A12）及以上；仅支持 iPhone，不支持 iPad。真机测试矩阵至少覆盖：1 台小屏机型（iPhone SE 档，验证 Dynamic Type 与窄屏布局）+ 1 台主流机型。

**依据**：BLE 工具场景对硬件无特殊要求（BLE 4.2 已足够，目标设备为经典 BLE 外设）；小屏是最容易暴露布局缺陷的验收面。

**影响**：UI 设计稿需提供小屏宽度（320pt 级）与最大 Dynamic Type 的适配规则；无架构影响。

**决策人**：产品。闭合时点：M0。

### 7. 每类设备的标准测试固件

**推荐结论**：为每条 OTA 验收线建立"可重复验证对"（当前版本 → 目标版本，必要时可回退/重刷），共 5 条固件基线，每条登记 source branch/tag/commit 与产物 hash：

| 基线 | 构建配置（已核实） | 用途 |
| --- | --- | --- |
| MPS100 | `LoRaWAN_ParkingSensor/USER/config.h`：`#else` 分支，`PROCT_NAME "MPS100"`、hw `0x0B`、sw `0x1C` | 首条 OTA 验收线（M6） |
| EPS100 | 同文件 `#if 1` 分支，`PROCT_NAME "EPS100"`、hw `0x0A`；**需固件组提供该构建配置的产物与基线** | 第二条验收线（M7） |
| UDS100 | `PROCT_NAME "UDS100"`、hw `0x02`、sw `0x0A` | 第三条验收线（M7） |
| SVC100 | `PROCT_NAME "SVC100"`、hw `0x0D`、sw `0x0D` | 第四条验收线（M7） |
| 各设备旧版本 | 从固件仓库历史 tag / `USER/Firmware/` 产物中选定，登记 hash 与来源 | 构造"升级到新版本"场景 |

**依据**：firmware-traceability.md §2/§3 要求"每个 OTA 测试目标必须映射到 source branch、tag、commit 或可复现构建配置"；§7 已将"EPS100 source baseline"列为待裁决项。上述版本常量已在本设计阶段对 `USER/config.h` 逐一核实。

**影响**：
- 需固件组配合：确认 EPS100 构建配置、提供各设备旧版本固件来源；
- 该项直接阻塞 M6/M7 真机验收，但不阻塞 M3–M5 开发；
- App 侧 v1 不做固件二进制级设备-固件配对校验，但按评审建议（2026-09-04，P1-7）增加**弱校验 + 强警告**：选择文件时按文件名前缀与设备型号比对，不匹配即弹强警告（明示"固件与设备型号可能不匹配，升级失败可能导致设备无法使用"），需用户二次确认；升级报告记录所选文件与设备型号。

**决策人**：固件 + 测试 + 研发。闭合时点：不晚于 M5 结束。

### 8. OTA 后预期版本格式

**推荐结论**：机器可读判定 = OTA 完成并重连后，通过 `0xFF` 状态查询读取版本 TLV `0x01`，解析出的版本值与"期望版本"一致才判 OTA 成功。期望版本来源 v1 采用"用户确认制"：选择固件文件后，升级确认弹窗预填期望版本（可编辑），完成后自动比对，不一致判失败并在结果页显示"旧版本 → 实际读到的版本"。

**依据**：
- 固件版本由 `USER/config.h` 的 `HARDWARE_VER`/`SOFTWARE_VER` 定义（已核实：UDS100 `0x02/0x0A`、MPS100 `0x0B/0x1C`、SVC100 `0x0D/0x0D`），经 `callback_BLEQuery()`/`callback_BLESearch()` 以 TLV `0x01` 上报——这是唯一稳定的版本读取通道；
- 无法假设固件 `.bin` 文件内嵌可解析的版本段：M3 需核对 Bootloader flash 布局与 `.bin` 头部是否含版本信息；确认前不得承诺"从文件自动解析版本"；
- 需求 8.4 明确"仅进度条 100% 不算成功"，版本比对是验收闭环的最后一环。

**影响**：
- OTA 状态机终态固定为 `verifyingVersion → success/failed`（大纲 §8）；
- 升级确认弹窗、结果页需要期望版本输入与比对展示（P-04）；
- 测试向量需包含版本 TLV 样例（各设备 `0x01` 载荷格式列入 M3）。

**决策人**：研发 + 测试。闭合时点：M0 定判定规则；"从 .bin 解析版本"作为 M3 核对项。

### 9. 分发方式

**推荐结论**：研发期（M4–M8）使用开发签名直装（注册测试 iPhone UDID）；对外试用与现场验证使用 TestFlight；不采用企业签名。TestFlight 所需的 App ID、证书、Profile 在 M6（MPS100 OTA 通过）后启动，不提前消耗。

**依据**：需求第 13 章已声明 Apple Developer Program 账号具备、签名分发事项暂缓；开发签名是唯一满足"真机 BLE/OTA 每日验证"的最短路径。

**影响**：
- **M4 前置硬条件**：至少 1 台 iPhone 完成开发签名，否则 BLE 骨架无法真机验证——需尽早处理 Apple 开发者后台（App ID、开发证书、设备注册）；
- 分发策略不影响架构与 UI 设计。

**决策人**：研发管理。闭合时点：M0 定策略；开发者后台操作在 M3 期间完成。

### 10. App 名称与 Bundle ID

**推荐结论**：显示名 `HKT BLETools`（中英文一致，与 Android 应用名对齐）；工程名/模块前缀 `HKTBLETools`（延续 `ios/HKTBLETools.xcodeproj` 既定裁决）；Bundle ID `com.hkt.ble.bletools.ios`。

**依据**：需求第 14 章默认建议；与 Android `applicationId com.hkt.ble.bletools` 同族，`.ios` 后缀保证与既有 Android 包名及未来统一域名分配不冲突；Bundle ID 全局唯一（含 App Store 维度）。

**影响**：Bundle ID 一经用于 App ID/证书/Profile 即不易更改，必须在 M4 真机签名前敲定；本地化资源中显示名走 `InfoPlist.strings`（CFBundleDisplayName），中英文可各自覆盖。

**决策人**：研发管理。闭合时点：M0。
