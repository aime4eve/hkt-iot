## 总体结论

**有条件通过。**

三份文档整体质量高：OTA 六阶段与 §8.5 十个异常场景逐条映射完整、S-5/S-7 连续性状态有 UI 落点、协议术语隔离（Debug 页除外）符合验收标准 5、OTA 成功判定与"100% 不算成功"基线一致、未发现任何跨平台或提前实现代码的倾向。条件如下：

1. 闭合 P1-1（§10.2 十类错误在页面状态集的逐类落位）；
2. 闭合 P1-2（UI 计划自行新增的两条验收门需产品确认并回写需求）；
3. 闭合 P1-3（固件-设备配对不校验的不可逆风险需在 P-04 明确防线）。
以上均不推翻页面清单与裁决方向，修订后即可进入 D2 线框阶段。

## 分级发现清单

### P0 阻塞（0 条）

无。

### P1 重要（3 条）

**P1-1 §10.2 十类错误未在页面状态集中逐类落位**
- 文件/章节：ui-design-plan §3 P-02/P-03 状态集、§7.3；依据：需求 §10.2（十类错误"不允许统一展示为失败"）与 §3.3 验收标准 1。
- 问题：UI 计划 §7.3 与 §10 表声称"错误十分类、每类人话文案+建议动作"，但只声称落点在"P-04/P-08 错误态"。十类中至少三类找不到页面状态：④ 连接错误之外的 ⑥写入失败（仅 P-06 Debug 覆盖，普通会话写入失败无落点）、⑦协议 CRC 错误、⑧响应格式错误。P-03 状态②只定义了"轮询暂无响应"，而"响应有数据但 CRC/格式错"是不同状态，按现稿会落入哪一态未定义。
- 建议：在 P-02/P-03 状态集中显式补充"通信数据异常（校验/格式）"与"写入失败"态及其建议动作；在 §7.3 增加一张"§10.2 十类 → 页面状态 → 文案 key"映射表，作为 D5 文案表的骨架。

**P1-2 UI 计划自行新增两条验收门，超出需求 §3.3/A-00 口径，未回写需求**
- 文件/章节：ui-design-plan §8 设计验收清单（加粗两项）；依据：需求 §3.3 六条验收标准、§12.1 A-00。
- 问题："每个错误状态附带建议动作"与"OTA 结束生成可导出的升级报告"是 UI 计划对自身的加码（§10 称"本次新增/升级为验收项"）。升级报告还隐含新的持久化与导出能力（S-7 最小持久化集只列"OTA 历史报告"，勉强能挂靠，但导出格式、存储上限、是否进日志均未定义）。这两项若在 M1 评审门按 UI 计划口径验收，而 A-00 按需求口径验收，会出现双口径。
- 建议：二选一并落文档——(a) 产品确认采纳，回写需求 §3.3/A-00 与 §9.2，并补报告的格式/导出/保留策略；(b) 降级为"设计目标/非验收项"。不要以当前状态进入 M1 评审。

**P1-3 OTA 文件与设备不配对，跨设备误刷风险与自身"OTA 更可信"目标矛盾**
- 文件/章节：open-items-recommendations Q7 影响（"App 侧 OTA 文件选择不校验设备-固件配对，v1 由使用者保证，UI 提示设备型号与所选文件名"）；ui-design-plan §3 P-04 阶段①②。依据：需求 §16"OTA 是不可逆现场操作"、§10 表"OTA 更可信/防呆"。
- 问题：v1 面向现场工具场景，选错文件刷错设备是本清单内最严重的不可逆风险，而现防线仅是"提示型号+文件名"，与 §10 的防呆定位不匹配。裁决建议未讨论折中方案。
- 建议：v1 至少落地一道低成本弱校验或强警告，例如：(a) M3 核对 `.bin` 头部是否含 hw/sw 版本（Q8 本已要求核对该点），若可读则做设备-文件匹配强警告；(b) 若头部不可读，升级确认弹窗（P-04 阶段②）要求"设备型号与文件名模式一致"作为默认拦截 + 显式"仍要继续"逃生口。将此从 Q7 影响中升格为明确设计项。

### P2 建议（6 条）

**P2-1 UI 计划把 v0.1 未确认裁决当作既定基线，依赖风险未标注**
- 文件/章节：ui-design-plan §3 P-04 阶段①⑥（期望版本预填可编辑、自动比对）、P-05"v1 状态：禁用占位"；依据：open-items-recommendations 头表标注"v0.1 Review Draft……未确认前不进入对应开发"，需求 §14 十项全部仍开放。
- 问题：P-04 三处结构直接依赖 Q8 结论、P-05 的 v1 定位依赖 Q1 结论。计划虽用"（Q2 推荐…）"等字样弱标注，但 P-04/P-05 的页面定义本身已按推荐结论写死，未给出"若 Q8 改为从 .bin 解析版本"的变更影响说明。
- 建议：在 ui-design-plan §1 或各页加"裁决依赖表"（Q1→P-05/P-09，Q8→P-04①②⑥），并注明 D2 线框评审前 Q1/Q8 必须闭合（与裁决文档"闭合时点 M0"一致）。

**P2-2 需求 §8.3 第一阶段"待发送"在 P-04 无显式状态**
- 文件/章节：ui-design-plan §3 P-04；依据：需求 §8.3 第 3 条阶段列表（待发送/传输中/完成包/等待重启/重新连接/版本确认）。
- 问题：P-04 拆为 ①选择固件 ②确认 ③传输中…，其中"已选有效文件、待触发升级"的"待发送"态被①②吸收，页面状态集未显式定义（例如选好文件后 App 崩溃恢复、或确认弹窗关闭后的界面态）。D4 原型与研发状态机逐态核对（大纲 §8）时可能对不齐。
- 建议：P-04 阶段①显式拆出"待发送（已选有效文件）"子态，与架构状态机命名对齐。

**P2-3 S-2"响应慢 vs 无响应"在 P-03 未区分**
- 文件/章节：ui-design-plan §3 P-03 状态②；依据：需求 §18 S-2（LoRa 上行共用主循环，会话中可出现秒级延迟，必须区分"响应慢"与"无响应"）。
- 问题：状态②只写"轮询暂无响应（最后有效值+时间戳）"。单次超时（可能秒级自愈）与连续无响应在 UI 上如何分级（如"更新延迟"vs"设备无响应"）未定义，而这正是 S-2 的验收点。
- 建议：P-03 状态②拆为"更新延迟（仍在重试）"与"连续无响应（建议检查设备）"两级，阈值与架构大纲 §7.1 对齐。待核实：具体分级阈值属架构大纲职责。

**P2-4 Q7 测试固件闭合时点偏晚**
- 文件/章节：open-items-recommendations Q7（"不晚于 M5 结束""不阻塞 M3–M5"）。
- 问题：固件基线需固件组提供 EPS100 构建产物、各设备旧版本来源与 hash，外部依赖周期不可控；若 M5 末才闭合，M6（MPS100 OTA）开工即被卡。建议提前到"不晚于 M3 结束"，与固件追溯基线（M3）同批完成，成本最低。

**P2-5 旧版本固件回刷可行性未核实，"可重复验证对"可能不成立**
- 文件/章节：open-items-recommendations Q7（"必要时可回退/重刷"）。
- 问题：需求 §4.1/S-5 表明 Bootloader 仅校验 SP、有更新标志机制，是否接受降级镜像（旧版本→新版本→旧版本循环）未核实。若 Bootloader 拒绝低版本，"可重复验证对"退化为单向，多条验收线的重复执行策略需重排。待核实：`BootLoader/main.c` 版本/SP 校验逻辑。建议在 Q7 闭合时点前追加该项核对。

**P2-6 设备列表显示"Identifier 后缀"弱化了对现场识别有用的信息，且与需求 §5.2 表述不一致**
- 文件/章节：ui-design-plan §3 P-01（"名称、Identifier 后缀、RSSI 信号图标"）；依据：需求 §5.2 第 7 条（显示设备名、MAC/Identifier、RSSI）。
- 问题：CoreBluetooth 拿不到 MAC，peripheral identifier 是本机随机 UUID，后缀对现场"认设备"价值有限；需求写的是"MAC/Identifier"完整值。二者口径不一致，且暴露了 Q4（目标定位）依赖广播原始数据的同一根源问题。
- 建议：需求 §5.2 增补 iOS 侧说明（显示本机 Identifier 完整值 + 后缀仅在卡片折叠态显示），并把"广播包中是否含可作现场标识的字段"并入 Q4 的 M3 核对项。

### P3 备忘（5 条）

**P3-1 Q1 影响面漏列 P-09**
- open-items-recommendations 结论总览 Q1 影响面仅写"UI P-05"，但 Q1 同时裁决校准（P-09 入框与否，见 ui-design-plan D2）。建议影响面补"UI P-09"。

**P3-2 iPhone 不同尺寸适配的交付规则未进 UI 计划**
- 需求 §3.3 范围 6 要求"iPhone 不同尺寸适配"；ui-design-plan §1 假定基线未列尺寸适配，Q6 只在裁决文档影响中提到"320pt 级 + 最大 Dynamic Type 规则"。建议在 D3 交付物中显式加"小屏（SE 档宽度）适配规则"，保证 M1 交付闭合需求 §3.3。

**P3-3 交互说明对"按钮状态"的系统化不足**
- 需求 §3.3 交付物 5 要求定义按钮状态；ui-design-plan §5 只覆盖禁用条件与保护，未按"每个组件 normal/disabled/loading/error 四态"逐按钮枚举（§6 组件表有四态但两者未勾连）。D5 组件状态表产出时补映射即可。

**P3-4 VoiceOver 未提及**
- 需求与 UI 计划均未要求 VoiceOver。内部工具可不做验收项，但建议 OTA 阶段切换与结果页至少加 accessibility 宣告（低成本、对现场戴手套/不看屏场景有实际价值）。备忘，不阻塞。

**P3-5 排期偏紧**
- ui-design-plan §9 三周完成 D2–D5（三套设备模板 × 浅深 × 中英 + 可点击 OTA 原型 + 双语文案表），且 F-03/F-04 优先策略正确；但 W3 同时承担 P-06/P-07/P-08 高保真、Token、文案表与验收评审，单周风险高。建议预判 W3 溢出时的降级顺序（文案表与 Token 不可降，P-08 可并入 P-01 权限态）。

## 检查单结论

### A. 需求 §3.3 八项交付物在 UI 计划的覆盖

| 交付物 | 覆盖情况 | 结论 |
| --- | --- | --- |
| 信息架构 | ui-design-plan §2（导航结构、feature surface、P-08 全局拦截） | 覆盖 |
| 关键用户流程 | §4 F-01~F-08，覆盖扫描/连接/状态/OTA 成功失败恢复 | 覆盖 |
| 低保真线框图 | §8 D2（计划中，未产出——本阶段正常） | 计划覆盖 |
