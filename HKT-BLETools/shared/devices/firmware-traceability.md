# Firmware Traceability Baseline

## 1. Purpose

iOS features, protocol contracts, test cases, UI states, and software design documents must be traceable to the firmware implementation that actually accepts and returns the corresponding data.

The Android app is a compatibility reference, not the protocol authority. When Android and firmware disagree, the firmware source and the selected firmware release define the implementable contract. Any intentional iOS-side restriction must be recorded separately.

## 2.1 M3 Contract Baseline (2026-09-06)

Verified against `HKT-Firmwares/in-house/LoRaWAN_{Ultrasonic_Distance_Sensor,ParkingSensor,Solenoid_Valve_Controller}` on branch `nix/ios-v1-design`; golden vectors in `shared/fixtures/*.json` generated by `HKT-BLETools/scripts/fixtures/gen_fixtures.py`; iOS core implementation `HKT-BLETools/ios/Package.swift` (CoreProtocol/CoreOTA/CoreDevice, 29 XCTest green via `swift test`).

1. Response stream is `hkt(3) 0x00 seq(1) records`; records are `type(1) + fixed-size value` — **no length byte, no command byte, no CRC**. Unknown type ⇒ data-abnormal (no safe skip).
2. All multi-byte values big-endian; ACK record is `0xFF 0xFF`; signed values use sign-bit rules (16/24/32).
3. `0xFF/0xFE/0xFD/0x01` app commands carry a 4-byte filler payload; power byte at payload[3] (firmware reads frame offset 10).
4. Config payloads: DC200Family `len=4` = period(2 BE, 0/1-1440) + parkMode(1, 0-2); UDS100 `len=9` = report(2)+GPS(2)+low(2)+high(2), ranges 1-1440 / 0|10-1440 / 30-4500 / 0|30-4500, invalid ⇒ **whole config silently rejected (no ACK)**; SVC100 `len=8` = vol+port+stable+smartPower+timezone+period(2), timezone>26 ⇒ early return **without ACK** while invalid period still ACKs (asymmetry — vector TX-SVC-CFG-002).
5. SVC100 timezone encoding: 0-12 positive, 13-24 = −(tz−12), 25=+03:30, 26=+05:30.
6. `ble_sleep_mode` defaults to 0 (connected device does not sleep); toggled only by BLE debug text commands `switchBLESleepON/OFF` (ParkingSensor communicate.c). `MAX_WAIT_SLEEP_TIMEOUT=60` has no call site in the current checkout — treat as inert.
7. Bootloader ACK = `hkt cmd(1) count(2 BE) bootload(8)` (14 B); first request is (0x02, 0); completion ACK is (0x03, 0) triggered by the size threshold, not by an app "finish" command; a cmd-0xFF packet forces the flush.
10. BLE time sync `0x06` (2026-09-06, all three projects verified): guard `data[5]==4 && data[6]==6` with stamp read from `data[7..10]` (4 B BE) — **the declared len field must be 4 (data length only, NOT cmd+data)**; Android ships the same quirk. `stamp==0` silently ignored (no ACK). Offset semantics differ: UDS100 and DC200Family add fixed UTC+8; SVC100 adds its configured timezone (`device_t.timezone`, incl. half-hour codes) and re-arms the local schedule clock. All three ACK on success. App requirement (2026-09-06, user): sync the **phone's** current time — send `System.currentTimeMillis()/1000`-style Unix seconds from the phone (same as Android's sync button); iOS must NOT pre-apply any timezone offset.
8. Pending external baselines: BLE transparent-bridge module model/config (vendor-side, absent from MCU source); EPS100 build baseline (`#if 1` branch artifact); `ble_sleep_mode` retention across reboots (not observed persisted).
8b. **OPEN firmware defect — SVC100 realtime-task `0x03` pulse width (firmware team CONFIRMED 2026-09-09, ruling = 2-byte read; firmware code change pending on their side)**: the `data[5]==7 && data[6]==3` branch (BLE entry `communicate.c:1649`, shared dispatch case `DATATYPE_SET_CLOCK_SCHEDULE` `communicate.c:556`) reads the pulse as 3 bytes (`srcHex[5]<<16|srcHex[6]<<8|srcHex[7]`) while the len-7 gate only carries a 6-byte payload, so `srcHex[7]` is the CRC high byte and the on-device pulse becomes `(sent_pulse<<8)|crcHi` (e.g. send 100 → device gets ~25 787). **Agreed fix (backward compatible): read 2 bytes (`pulse = srcHex[5]<<8|srcHex[6]`) in BOTH places, keep the len-7 gate** — Android V3.21 frames keep working unchanged. Do NOT widen the gate to 8: that would silently drop every shipped Android frame. App contract unchanged: send exactly 6 payload bytes (fixture `TX-SVC-TASK-001`). Evidence: Android `Communicate.kt` cmd 0x03 block; iOS fixture `TX-SVC-TASK-001`; byte-walk in the 2026-09-07 review. See item 9.
9. SVC100 valve tasks (2026-09-06, re-verified 2026-09-07 from `SVC communicate.c`): realtime `0x03` frame = len 7 (= cmd + 6-byte payload): valve(0 both/1/2) + state(0/1) + duration(2 B BE, seconds, 0 = no auto-stop) + pulse(2 B BE, 0-65535) — **app contract sends exactly 6 payload bytes, byte-identical to Android V3.21** (fixture TX-SVC-TASK-001). ⚠️ Firmware quirk (filed to firmware team): the `data[5]==7` branch reads the pulse as 3 bytes (`srcHex[5]<<16|srcHex[6]<<8|srcHex[7]`), over-reading the CRC high byte, so the on-device pulse count becomes `(pulse<<8)|crcHi`; the len gate must be 8 (3-byte pulse) or the read must be 2 bytes. **busy (local schedule running) is silently ignored — no ACK**, so the app must treat a 2 s timeout as "rejected: busy". Timed task `0x04` payload = id(1-16, slot selectable, writing overwrites) + valve(0-2, both-valve allowed) + state(0/1) + pulse(2 B BE) + start/end minute-of-day (2 B BE each) + repeat mask ≤ 0x7F, **bit0=Monday … bit6=Sunday** (`(wday?wday:7)-1`); any invalid field ⇒ silent return without ACK (firmware does NOT validate end>start — the app must pre-validate it); valid ⇒ persisted to flash + ACK. Delete `0x05` payload = id 1-16, `0xFF` = delete all (force-stops a running task); ACK always. The schedule table has **no BLE read-back** — `0x3D` task sync exists only on the LoRaWAN platform path (`Device_ReportLocalTaskData` → uplink ring buffer), so the app must keep a local mirror and say so in the UI. BLE transparent-bridge module model/config (vendor-side, absent from MCU source); EPS100 build baseline (`#if 1` branch artifact); `ble_sleep_mode` retention across reboots (not observed persisted).
9b. SVC100 port function (2026-09-07 re-verified): config `0x02` accepts any port byte (`device_t.port_mode = valveMode`, no firmware-side range check); the UI vocabulary is 7 values `0x00,0x01,0x02,0x03,0x81,0x82,0x83` (per-port pulse/switch combos; 0x80 bit = stable time applies), labels per Android `spinner_items_valve_mode`. Stable-time field is editable only in 0x80-bit modes (Android `updateStableTimeEditor`). Status record `0x3A` park state: current firmware assigns only 0/1; Android additionally maps 0xFF→"Covered" and others→"Unknown" (defensive — keep in iOS). UDS100 tilt `0x0E`: firmware sends `angle*100` as u16 (`device_t.angle * 100`) → display = raw/100 (Android divides by 100). Overflow `0x47`: 0=normal/1=low threshold/2=high threshold/0xFF=invalid.

## 4. Protocol Evidence

### 4.1 Common transport

The application prefix `68 6B 74` and the Bootloader suffix `62 6F 6F 74 6C 6F 61 64` appear in all three firmware projects. The Bootloader parser checks CRC16 and rejects bad frames.

The normal application command handlers parse the binary `hkt` frames by command and payload length. The current application handlers were not observed to reject a frame solely because the Android-provided CRC bytes were wrong; nevertheless, iOS must continue to build and send CRC exactly like Android unless firmware explicitly declares CRC optional. iOS tests must distinguish these two statements:

1. iOS builds a valid CRC.
2. Firmware application code validates the CRC.

Only the first statement is currently proven by the Android behavior and App-frame implementation; the second must be verified per firmware release before being claimed in a test.

## 5. Traceability Rules

Every feature must carry the following links:

| Link | Meaning |
| --- | --- |
| `FR-*` | Functional requirement |
| `FW-REF-*` | Firmware repository, baseline, file, function, and behavior |
| `VEC-*` | Shared request/response or state-transition vector |
| `TC-*` | XCTest or integration test |
| `SD-*` | Software design section |
| `UX-*` | UI screen, component state, or interaction flow |

A feature may enter implementation only when all five links exist or the gap is explicitly accepted as an architecture-only extension.

Test vectors must include:

```json
{
  "id": "SVC-CONFIG-001",
  "device": "SVC100",
  "firmwareBaseline": "<tag-or-commit>",
  "androidReference": "android/app/src/main/java/com/hkt/ble/bletools/Communicate.kt#streamDevice(0x02)",
  "firmwareReference": "HKT-Firmwares/in-house/LoRaWAN_Solenoid_Valve_Controller/USER/Drive/communicate.c#fromBleDataHandle",
  "request": "<hex>",
  "expectedAck": "<hex>",
  "postCondition": "device reports the configured values",
  "iosTest": "SVC100ProtocolTests/testBasicConfigurationFrame"
}
```

## 6. Verification Gates

### 6.1 Contract gate

For each device:

1. Confirm model name from `USER/config.h`.
2. Enumerate supported TLV types from `USER/Drive/include/communicate.h`.
3. Extract status fields from the BLE query callback.
4. Extract accepted commands, payload lengths, field offsets, ranges, side effects, and ACK behavior from `fromBleDataHandle()`.
5. Extract persistence and time semantics.
6. Extract OTA behavior from `Compents/BootLoader/uart.c`.
7. Compare the result against Android and record every difference.

### 6.2 Test gate

1. Generate golden vectors for normal, boundary, and rejected values.
2. Add XCTest cases for frame construction and response parsing.
3. Add OTA state-machine cases for request, data packet, final padding, completion, reboot, reconnection, and version confirmation.
4. Add negative cases for malformed length, unknown command, invalid range, missing ACK, and CRC failure where applicable.
5. Record expected behavior when firmware logs an error but does not return a protocol-level negative ACK.

### 6.3 Design gate

The iOS software design must map every UI state and use case to:

1. A firmware reference.
2. A protocol command or response type.
3. A device capability flag.
4. A test case.
5. A ViewModel state.

The software design review is not complete if a feature exists only because Android has it.
