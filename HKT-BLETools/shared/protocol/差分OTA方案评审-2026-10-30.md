## 一、事故背景（评审动因）

170 台地磁设备升级最新固件后，19 台能扫描、能建立 GATT 连接，但应用层"开机"失败。**2026-10-30 确认：19 台真变砖**（无法再走无线升级；拆机监控确认完全无法工作）。

- 损坏层判定：**bootloader 层嫌疑最大**。若仅 APP 区传输中断，bootloader 仍在等待重传、无线重推可救；实际无线通道全灭，说明 bootloader 已无法工作。
- 机制候选（按嫌疑排序，待取证定案）：
  1. 本次升级包含 boot 替换（两段式升级），19 台死在 boot 区擦写窗口被打断——与"升级 boot 需要两次、出问题更大"的已知风险表述直接呼应；
  2. OTA 写越界覆盖 boot 区：boot 区无任何写保护，镜像长度/地址异常或发错包可写穿 boot；但同包 151 台成功，此解释弱于"窗口被打断"；
  3. 擦写窗口掉电落在 boot 区（仅当升级动 boot 才致命；落 APP 区则 bootloader 等待、仍可救）。
- 判断方法论教训：蓝牙广播/GATT 由 DA14531 透传模组独立完成，与主控死活无关，**日志无法区分"boot 活着等重传"与"boot 已死"**（两者都是"能扫能连、零收帧"）——变砖类结论必须有线取证定案。
- **恢复路径**：拆机后 ST-LINK（SWD）重刷完整 boot+APP 镜像（RDP 读保护未锁即可，L431 默认未锁）。
- **取证三问（防再发定案用）**：①本次升级包是否包含 boot 替换？②拆机监控手段与所见（SWD 能否连接；boot 区内容全 FF=被擦 / 乱码=被写坏）？③App 端失败时进度停在哪一步？

## 二、现行 OTA 机制的问题（代码核实）

| # | 问题 | 证据 |
|---|------|------|
| 1 | 原地覆盖写：bootloader 边收边擦边写直接覆盖 APP 区（0x08004000 起，页 2KB），无暂存区、无回退 | `BootLoader/uart.c`、`flash.c` |
| 2 | 无整包校验：跳转前只验栈顶 SP 合法性，镜像内容无 CRC | `flash.c AppProgramRun()` |
| 3 | 收尾帧强依赖：必须收到 cmd=3 finish 帧才跳转，漏发/传输中断 = 设备永驻 bootloader | 协议审计 ❌-4 |
| 4 | boot 区无写保护：任何越界写/发错包都能物理覆盖 boot，一坏即死局 | 本次 19 台事故直接根因之一 |
| 5 | 传输粗放：128 字节停等式，约 11 秒无包整场重来；现场 170 台密集蓝牙环境下传输中断概率高 | `BootLoader/uart.c` |

## 三、评审结论（终版）

**总体判断：方案方向正确**——外部 Flash 暂存 + boot 只管引导 + 失败回退是标准双区升级思路，正补齐现行机制"原地覆盖/无校验/无回退"三个窟窿。按下表修正后可进入规格文档阶段。

> **裁决记录（2026-10-30 用户，已并入下文）**：①新固件确认口径 = APP 执行后经通讯读回版本号判定（P1-2）；②boot 区保护采用软件判定，不使用硬件写保护——避免烧录器无法更新烧录 boot 区（P0-5）。

### P0（必须修正，6 条；①~④ 首评，⑤⑥ 系 19 台变砖事故增量）

1. **断电变砖窗口**：流程末步"搬 APP 页并写入 APP 区"中途断电 → 内部 APP 毁；重启进差分升级又要以内部 APP 为底包合成 → 底包已没 →"回退旧固件"回无可退。**修法**：boot 进入差分升级后先校验外部 NewFW 区是否已有完整通过 CRC 的新固件（搬运被打断时它完好）——有效则跳过合成直接搬运；搬运幂等，重复无害。
2. **分区表数字自相矛盾**：BOOT 标 32KB 但地址 0x0000-0x5FFF 实为 24KB；APP 标 220KB 但 0x6000-0x3EFFF 实为 228KB。若真意 32KB，APP 基址应为 0x8000。另：现役 boot 仅 16KB（0x08000000-0x08003FFF）、升级标志页 0x0803F800（魔数 0x12345678），引导区是否扩容、标志格式如何迁移须在设计文档写明；内部 Flash 地址应带 0x08 前缀（0x08000000 起）。
3. **底包校验须内容级**："读并校验固件信息是否匹配"只对版本号不够——版本对但底包内容残（如 APP 区半残设备）时会合成出"CRC 通过的错误固件"。补丁头必须携带底包全文 CRC/哈希，合成前全文校验。
4. **外部 NOR 硬件前提核实**：固件 `config.h` 中 `NOR_FLASH_ENABLE 0`（sfud 驱动在但禁用）。方案布局需外部 NOR ≥512KB（Patch 256K + NewFW 256K）。存量 170 台板上是否贴片、容量多少待核实——决定本方案对存量是否可行。
5. **boot 区软件禁写（全路径地址检查）**【10-30 增量；原提硬件写保护 WRP，同日用户裁决改为软件判定——硬件写保护会使烧录器/ST-LINK 无法直接擦写 boot 区，产线不可接受】：**所有**写内部 Flash 的路径都必须带 boot 区地址检查，不止 boot 一处——①boot 的 OTA 写入/擦除函数：目标地址 < APP 基址（0x08004000）直接拒绝；②**APP 侧 Flash 驱动统一封装并做同样检查**——本次事故候选机制之二恰是运行态写越界，现固件 APP 直接调用 Flash 驱动（如写标志页），不经过 boot，只改 boot 一处拦不住 APP 运行态的误写；③App 侧镜像头声明区域校验见 P0-6。裁决后残余风险 = 绕过封装直写 Flash 寄存器的严重缺陷不受保护，由 P0-6"boot 升级只进产线"纪律对冲。
6. **boot 升级只进产线 + App 侧镜像区域校验**【10-30 增量】：①App 侧校验固件镜像头声明的目标区域，含 boot 区一律拒绝推送（存量继续走旧通道前先落地）。boot 替换的无保护窗口经核实不可消除（STM32L431RC 为单 bank，无 DBANK/硬件 bank 切换；boot 区亦不作硬件写保护——见 P0-5 裁决）→ **boot 升级只允许在产线进行，现场升级包永不携带 boot 替换**；boot 按最小化设计，把"几乎永不需要升级"作为设计纪律。

### P1（建议优化，8 条）

1. **差分合成移出 boot，放 APP 内做**：方案原则"boot 仅用于引导"，但设计图把"搬运差分包并生成新固件"放在 boot 内（需内置差分算法 + RAM 窗口）。建议：设备 APP 收完差分包并校验通过后、复位之前，在 APP 内合成到外部 NewFW 并 CRC；boot 只剩"读标志 → 验 NewFW CRC → 搬运 → 回读校验 → 置跳转标志 → 跳转"。boot 是全设备唯一不能远程升级的代码，应最小化；算法升级不受 boot 限制；48KB SRAM 流式合成宽裕；且合成全程不碰内部 APP，P0-1 的断电窗口归零。
2. **新固件确认机制（裁决口径：通讯读回版本号）**：boot 只做搬运，确认由 APP 返回执行后经通讯完成——新固件启动后照常上报版本号（现有 0xFF 轮询记录流/版本记录已含版本号，无需新增命令），手机端读回版本 == 目标版本即判定升级成功（即 bootloader-ota.md 既有验收标准的机制化）。固件侧闭环建议：boot 搬运+回读校验通过后写 VAR"待确认（含目标版本）"并置尝试计数；新 APP 首次版本上报成功即回写"已确认"；boot 见"待确认"且连续 M 次复位仍未确认 → 不再跳转、驻留并开放 OTA 通道等重刷。**此兜底建议保留**：否则"新固件起不来"时更新标志已被清、设备无法再进入 OTA 模式，将重演本次变砖。边界说明：版本号确认防"搬运坏/起不来"，防不了"能跑但功能异常"——后者由 App 侧验收（读版本 + 基本功能可用）兜底。
3. **全量包兜底通道**：差分只能从"精确底版本 + 完好底包"升级，底包损坏/版本不明的设备（如本次 19 台）救不了。补丁头加类型字段（差分/全量），全量包直接当 NewFW 走同一搬运链——兼作现场恢复手段。
4. **断点续传**：分块（如 4KB）写外部 NOR、每块确认、重连后查询已收偏移续传，替换"约 11 秒无包整场重来"。
5. **VAR 区日志式防撕裂**：标志区用追加式记录（序号递增、取最新有效条），断电撕不坏；且仅在状态迁移时写入，正常启动零写入，避免每次开机擦一次扇区。
6. **传输层加固**：bootload 帧只有逐帧 CRC，整包校验落成补丁头字段（魔数/底版本/目标版本/底包 CRC/长度/整包 CRC/类型）；"连续 5 包校验失败退出"须定义设备侧半包清理与向手机端的错误码上报。
7. **看门狗**：现役 IWDG 软件启动、STOP 停计、超时约 8.7 分钟（256 分频 / 0xFFFF 重装）。boot 长时间搬运/校验期间必须喂狗；标志/校验逻辑正确时，狗复位本身即自愈路径。
8. **App（BLETools）配套**：①OTA 验收闭环——发完 finish 后自动等设备重新广播、重连、读版本比对，全部通过才算成功，失败当场报错、一键重推（协议文档 bootloader-ota.md 已有此验收标准，现场未执行到位是 19 台事故的直接教训之一，应做成 App 强制流程）；②救援模式——设备已处于 bootloader 等待态时跳过 0x01 直启 bootload 传输（救"传输中断但 boot 完好"类；对 boot 已损坏设备无效）；③差分新命令集 Android/iOS 双端实现；④诊断日志补应用层事件（命令收发/应答码/超时）——本次排障只有传输层日志、应用层完全不可见，是排障困难的主因。

## 四、落地顺序

1. **19 台处置**：SWD 重刷恢复 + 取证三问定案（见第一节）；同时排查其余 151 台有无"第一段写完、第二段未做"的中间态（有 = 下一批砖）。
2. **存量继续旧通道，但先装禁写 boot 双闸（P0-6）+ App OTA 验收闭环 + 救援模式**（纯 App / 小改固件，立刻降事故率；旧通道在此期间绝不推送含 boot 替换的升级包）。
3. **差分方案按第三节终版清单出规格文档**（分区表修正 / VAR 标志状态机 / 补丁头格式 / boot·固件·手机端三方职责 / 新旧 App 兼容矩阵 / **新 boot 烧录流程含上 WRP 步骤**），评审冻结后再动固件。
