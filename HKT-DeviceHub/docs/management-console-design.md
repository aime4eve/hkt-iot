## 1. 背景与目标

DeviceHub 的设备注册、通道健康、对账能力已在 API 层具备，但运维/实施人员没有可视化入口：当前靠 Swagger 调接口、psql 查库、mqadmin 看队列——本次 8 台设备接入实战中，每次排查都要在 4 个工具间切换。

控制台目标：**把"设备接入五层验证"和日常巡检收敛到一个页面级工具**，让非研发同事也能完成新设备接入与故障定位。

## 2. 用户与核心场景

| 角色 | 场景 |
|---|---|
| 实施工程师 | 新设备接入：预检 → 注册 → 确认数据入链 |
| 运维 | 每日巡检：通道状态、静默设备、滞后异常 |
| 运维/管理员 | 重名/脏数据治理：冲突清单 → 证据比对 → 清理（人工确认） |
| 值班 | 排障：某台设备"没数据了"→ 四级链路定位卡在哪层 |

## 3. 信息架构

单页应用（SPA），顶部全局导航 + 四个视图：

```
┌────────────────────────────────────────────────────────┐
│ HKT-DeviceHub 控制台   [tb-ws●][tb-rest●] LIVESTOCK 6│6  PARKING 14│14 │
├──────────┬──────────┬──────────┬──────────────────────┤
│ 工作台    │ 设备台账  │ 接入预检  │ 治理中心              │
└──────────┴──────────┴──────────┴──────────────────────┘
```

全局状态栏常驻：两个通道连接灯（tb-ws / tb-rest）、两项目"活跃/注册"计数。通道断开时全局横幅告警。

### 3.1 工作台（Dashboard）

**主视觉：数据链路拓扑图**（页面顶部 50% 区域）——呈现"从设备到路由项目"的端到端通畅能力：

```
[设备 LIVESTOCK×6]  ┐
                     ├─→ [NS] ─→ [TB网关 OC] ─→ [ThingsBoard] ─→ [DeviceHub] ─→ [RocketMQ] ─┬─→ [smart-livestock] ─→ [业务库]
[设备 PARKING×14]   ┘                                  ▲ 双通道：tb-ws ● / tb-rest ●         └─→ [smart-parking] ─→ [业务库]
```

- 节点：设备组（按项目聚合，显示活跃/注册数）、NS、TB 网关、ThingsBoard、DeviceHub（节点内嵌 tb-ws/tb-rest 双通道灯）、RocketMQ、两个业务后端、业务库
- **平台分组（泳道）**：TB 网关 OC 与 ThingsBoard 服务两个节点同属 ThingsBoard 平台——用一条标注「ThingsBoard 平台」的容器框（泳道）包住两者，保留两个故障域的独立呈现，同时一眼看出同属一个平台；原边上的"TB 认证有效"标注移为容器边界的标注。容器故障时边框变红/黄，内部节点保持各自状态
- 每条边带健康状态色（绿/黄/红），边上标注关键指标：NS 收帧、OC 映射项目数、TB 认证、WS 订阅数、MQ 24h 消息数、消费组 Diff（积压）、末次入库时间
- 数据流动效：链路正常时边上的光点动画流动；某段异常时该段变红、光点停滞，点击边/节点展开该段的排障提示（如"消费组积压→查单体 consumer 日志"）
- 数据来自 `/api/v1/channels/health` + 各段探测（MVP 阶段可用 health 聚合 + 定时探测，详见 API 映射）

**故障呈现模型**（拓扑图必须能表达真实故障，不只是演练）：

故障分两层四类，每段边/节点有对应的探测信号与判定阈值：

| 层 | 故障类型 | 探测信号 | 判定 |
|---|---|---|---|
| 网络层 | NS/MQ 不可达 | TCP 探测 | 连接失败 |
| 网络层 | TB 认证失效 | 登录接口 | 401 持续 >1min |
| 数据层 | OC 映射缺失 | 网关共享属性（只读） | 有 ACTIVE 设备的 NS 项目无映射 |
| 数据层 | WS 断连 / 回补停滞 | channels/health | 通道 down 或游标停走且对端有新帧 |
| 数据层 | MQ 积压 / 消费离线 | 消费组 Diff | Diff>0 持续增长或 >100 |
| 数据层 | 解码失败率上升 | 帧解析计数 | 5min 内失败率 >10% |

呈现规则：
- 故障边/节点：红色 + 光点停滞 + 故障徽章（一句话原因，如"TB 401 认证失效"）
- 点击故障段展开**故障详情面板**：故障类型、开始时间、持续时长、影响面（受影响设备数/项目、估计丢失或延迟的帧数）、建议处置、相关日志位置（容器名+关键字）
- 工作台异常关注列表同步出现对应条目，可点击定位到拓扑故障段
- 故障恢复后边自动转绿，详情面板记录"已恢复"及持续时长（本次会话内保留）

下方左侧：通道健康卡（WS/REST 状态、各项目追赶滞后、连续失败数）；右侧：项目卡片 × 2（活跃设备、noDataDevices、24h 帧数）；再下方：**异常关注列表**（静默超期设备、滞后>0 设备、待处理冲突）——巡检主入口，正常时显示"一切正常"空态

### 3.2 设备台账（Devices）

主表格 + 右侧详情抽屉。

列：EUI（等宽字体）、项目（LIVESTOCK/PARKING 徽章）、设备类型、TB 绑定状态、上报周期、最近一帧（相对时间）、四级健康灯（NS激活/有上行/TB解码/已入库）、状态（ACTIVE/PENDING/FAILED）。

- 筛选：项目、状态、健康灯、"只看异常"开关
- **模糊查询**：顶部搜索框，对 EUI / deviceCode / 设备类型做不区分大小写的子串模糊匹配，输入即过滤（防抖 200ms），命中子串高亮；与筛选条件叠加生效；清空一键复原
- 行内操作：详情、重新注册、对账定位
- 详情抽屉：注册信息（tbDeviceId、externalRef、capabilities）、游标与 last_frame_at、最近 10 帧摘要（从 MQ/库取）、四级健康时间线
- 四级健康灯（R-05）：●绿=已达 / ○灰=未达到；tooltip 给该级最后达到时间

### 3.3 接入预检（Preflight）（R-01）

页面主角是一个 EUI 输入框（16 位 hex 校验，大小写自动归一）。

提交后展示**五项体检报告卡**（仿照本次实战的排查路径）：

| 检查项 | 数据源 | 判定 |
|---|---|---|
| ① NS 设备与项目归属 | NS API | 存在性 + project/app + is_online + 帧计数 |
| ② 网关项目映射 | TB 网关 OC 共享属性（只读） | 该 NS 项目是否有 topic 映射 |
| ③ TB 设备唯一性 | TB tenant devices（大小写变体搜索） | 恰好 1 台=PASS；0 台=可创建；多台=列冲突候选 |
| ④ 设备 profile 匹配 | TB device profile | 类型↔profile 映射表核对 |
| ⑤ 本地/DeviceHub 绑定 | registered_devices | 绑定状态与游标 |

每项：PASS（绿）/ FAIL（红）/ WARN（黄）+ 一句话修复建议。全部 PASS 后出现"一键注册"按钮（调 register API）。报告可分享（URL 带 EUI 参数）。

### 3.4 治理中心（Governance）（R-04）

三个分区：

1. **重名冲突**：`TB_IDENTITY_CONFLICT` 清单。每条展开显示候选副本对比表（TB id、创建时间、最近遥测、遥测条数、当前被谁绑定），系统高亮"建议保留"（有遥测的）；「删除空副本」按钮二次确认后执行（记录操作日志）。删除后一键"重新注册"。

> **文案规则（全控制台通用）**：界面不出现内部枚举/错误码/技术代号（如 `TB_IDENTITY_CONFLICT`），一律用业务语言（如"同名设备冲突"），枚举值放 tooltip 或详情折叠区。台账/拓扑/预检同此规则。
2. **无数据设备**：noDataDevices 清单（注册但从无帧）+ 建议动作（现场确认/停用）。
3. **滞后异常**：追赶滞后 > 0 的设备列表（新语义：有新数据没追平才出现）。

### 3.5（P2，二期）命令控制台

设备详情抽屉内增加"下发命令"面板：命令类型下拉（按 capabilities）、payload 编辑、状态追踪（PENDING→SENT→ACKED/FAILED）。本期仅预留入口不实现。

## 4. API 映射

| 控制台需求 | 端点 | 状态 |

| 拓扑图各段探测（NS 可达/OC 映射数/TB 认证/MQ 积压/末次入库） | `GET /api/v1/channels/topology`（聚合接口） | ❌ 待建（R-10 扩展；MVP 可由 health + 前端分时探测拼装） |
| 设备注册/批量/对账 | `POST /api/v1/devices/register` `/import` `GET /reconcile` | ✅ 已有 |

## 5. 视觉设计令牌

运维工具默认深色主题（机房/弱光环境），全部颜色/间距走 CSS 变量，禁止硬编码：

```css
:root {
  --bg: #0d1117;            /* 页面底 */
  --bg-panel: #161b22;      /* 卡片 */
  --bg-inset: #0a0e14;      /* 表格内嵌/输入框 */
  --border: #30363d;
  --text: #e6edf3;
  --text-dim: #8b949e;
  --accent: #2f81f7;        /* 主操作/链接 */
  --ok: #3fb950;            /* PASS/在线/正常 */
  --warn: #d29922;          /* WARN/滞后 */
  --danger: #f85149;        /* FAIL/冲突/断连 */
  --mono: "SFMono-Regular", Consolas, monospace;  /* EUI/ID/时间戳 */
  --radius: 8px;
  --space-1: 4px; --space-2: 8px; --space-3: 12px; --space-4: 16px; --space-6: 24px;
}
```

状态灯统一：● 绿正常 / ● 黄警告 / ● 红异常 / ○ 灰未达。四级健康灯固定顺序：NS→上行→TB→入库。

## 6. 状态完备性要求（原型必须展示）

每个视图覆盖：loading 骨架、空态（"一切正常"/"暂无冲突"）、错误态（接口失败重试按钮）。台账至少覆盖：正常活跃、沉默设备（644，4h 周期）、无数据设备（30906）、待注册（PENDING）。

## 7. 非目标（v1 不做）

- 不做登录/权限体系（部署在内网，由既有网关兜底；v2 再议）
- 不做 TB/NS 数据的直接编辑（治理操作仅"删除空副本"且强约束）
- 不做命令下发（二期 R-12）
- 不做移动端适配（桌面优先，最低 1280px）

## 8. 分期

- **P0（本期原型）**：四个视图完整交互 + mock 数据（取自 dev 真实环境快照）
- **P1（实现）**：台账只读 + 健康总览 + 预检（依赖 R-01/R-11 后端接口）
- **P2（实现）**：治理中心（依赖删除接口）+ 二期命令控制台联动
