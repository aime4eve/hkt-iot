按现在掌握的固件、BLETools、NS/TB 和 SmartPark 实际情况，设备注册过程应该拆成五层，而不是一个“添加设备”动作。

**1. 生产/准备层：先有可信设备身份**

每一台地磁设备必须有唯一身份：

- `DevEUI` 来自 LoRaWAN 模组；
- `AppEUI/JoinEUI`、`AppKey` 必须在生产或备货阶段按设备唯一分配；
- NS 侧必须先用这组身份完成设备预注册；
- AppKey 不能使用当前样例固件里的公共测试值；
- 正式固件不应通过普通 BLE 状态接口暴露 AppKey。

这一步产出一份设备交付清单：`DevEUI / AppEUI / AppKey / 型号 / 频段 / 固件版本 / 入网配置`。NS 注册依赖这份清单。

**2. 现场配置层：BLETools 只负责本地确认**

现场人员使用 HKT-BLETools：

1. 扫码或输入 16 位 DevEUI；
2. 通过广播名后 6 位定位设备；
3. BLE 连接；
4. 读取硬件/软件版本、电量、车位状态、上报周期；
5. 配置工作模式和上报周期；
6. 执行地磁/雷达校准；
7. 必要时 OTA。

BLETools 解决的是“人员手里的 EUI 就是眼前这台设备”，并确认设备本体可用。它不是 NS 注册工具，也不是 SmartPark 注册工具。

**3. 网络接入层：NS/TB 先证明设备能上报**

设备上电后固件自动发起 OTAA 入网。入网成功后发出首帧。

此时必须在 NS/TB/DeviceHub 上确认：

- 该 `DevEUI` 已入网；
- 已出现真实首帧；
- 网关映射正常；
- profile/解码链路正确；
- 无同 EUI 冲突。

这一步产生的不是 SmartPark 的 `online`，而是**外部连通凭证**：

```
device_eui
source = NS / TB / DeviceHub
first_frame_at
last_frame_at
external_device_id
profile
gateway_id
verified_at
evidence_digest
```

这个凭证必须由 SmartPark 服务端查询外部平台获得，不能只靠前端提交“我看到了”。

**4. SmartPark 后置登记层：消费外部首帧凭证**

SmartPark 不应要求设备在 SmartPark 注册后再发一帧。正确顺序是：

```
现场安装 -> NS/TB 看到首帧 -> SmartPark 登记 EUI -> 允许预绑定
```

SmartPark 登记时：

1. 用户录入或批量导入 EUI；
2. SmartPark 服务端查询 NS/TB/DeviceHub；
3. 如果查到首帧，本地登记为 `found`；
4. 保存外部首帧凭证；
5. 不等待 SmartPark 自己收到下一条帧；
6. 后续 SmartPark 收到帧时，只刷新 `last_seen`、电量、信号等运行健康。

如果查不到外部首帧，SmartPark 可以登记为 `pending`，但向导必须明确提示“设备尚未在 NS/TB 上报”，不能允许进入预绑定。

**5. 业务绑定层：先预绑定，后投运**

登记成功的 `found` 设备允许预绑定：

- 新装场景：绑定到 `maintenance` 车位；
- 换绑场景：旧设备先解绑，车位保持 `maintenance`，再绑定新设备；
- 禁停区场景：区域保持草稿或未发布。

预绑定只建立“设备 ↔ 车位/区域”的业务关系，不改变车位运营状态。目标仍不可被车主使用。

后续投运门禁检查：

- 外部首帧凭证存在；
- EUI、NS/TB 设备 ID、SmartPark 绑定一致；
- 无重复绑定；
- 目标仍是 `maintenance`/草稿/未发布；
- SmartPark 健康状态可选展示，但不得把“注册后再来一条帧”当成唯一条件；
- 通过后才允许车位从 `maintenance` 恢复运营。

**状态模型建议**

SmartPark 内部可以对应为：

```
pending      已建档，但外部平台未见首帧
found        NS/TB 已确认真实首帧，允许预绑定
connecting   已预绑定，等待进入正式投运
online       SmartPark 已收到运行帧，健康可用
linked       已绑定目标并通过投运检查
offline      曾经在线，但超过预期周期无帧
```

关键是新增或明确两个概念：

- `external_first_frame_at`：NS/TB 首帧时间，用于证明设备硬件和无线链路可用；
- `last_seen_at`：SmartPark 实际收到的最新帧时间，用于运行健康。

两者不能混用。

**向导流程应改为**

现有向导四步可以保留，但语义调整：

1. **批量导入**
   - 服务端逐 EUI 查询外部凭证；
   - 显示“已发现首帧 / 未发现首帧 / 重复登记 / 平台不可达”。
2. **场地与网关**
   - 仅作上下文展示，不作为物理入网依据。
3. **注册与激活**
   - 有外部凭证：登记为 `found`；
   - 无外部凭证：登记为 `pending`，不允许下一步；
   - 不显示“等待 SmartPark online”。
4. **引导绑定**
   - 只允许 `found` 设备预绑定非运营目标；
   - 绑定成功显示“预绑定完成”；
   - 车位状态仍为 `maintenance`；
   - 后续帧只刷新健康。

**换绑流程**

1. 旧设备解绑；
2. 车位保持 `maintenance`；
3. 新设备必须已有 NS/TB 首帧凭证；
4. SmartPark 登记/查找新设备；
5. 预绑定新设备；
6. 投运检查通过后恢复车位运营。

**当前 4 台设备**

不需要删除重加。它们已经在 DeviceHub/TB 有首帧证据，只是 SmartPark 当前把它们登记成了等待本地首帧的 `pending`。正确处理是：

1. 按新设计回查 NS/TB/DeviceHub；
2. 生成外部首帧凭证；
3. 将 SmartPark 状态迁移为 `found`；
4. 允许进入预绑定；
5. 后续 SmartPark 收到帧后刷新健康。

核心原则一句话：**NS/TB 首帧证明设备能入网，SmartPark 登记是业务资产登记，车位投运是另一个独立门禁。三者不能混成一个状态。**
