# HKT-DeviceHub 平台管理功能需求

> 来源：2026-09-17 六台真实设备（2 台停车地磁、2 台牛羊追踪器、2 台瘤胃胶囊）接入实战。
> 每条需求都对应当天真实发生的问题，标注了事实证据。

## 一、经验教训（事实记录）

### L1. 共享 TB 租户的同名/脏数据是常态，不是异常
- `009569000003056c` 在 TB 有两台同名设备（一台有遥测、一台空壳）；`00956906001264af` 也有两台。
- 13 台试点设备批量注册时 6 台因重名被拒绝（`TB_IDENTITY_CONFLICT`），占比近半。
- 教训：设备重名在共享租户里会长期、反复出现，靠人肉发现不可持续。

### L2. EUI 大小写变体是隐蔽陷阱
- `00956906001264Af`（混大小写）与 `00956906001264af` 在 TB 是不同的设备名；DeviceHub 精确匹配查不到混写设备，于是新建了一台，造成"删完一台又冒一台"。
- 教训：EUI 规范化（全小写）必须是平台级强制规则；查找必须覆盖大小写变体并显式报歧义（livestock 侧已有三变体匹配的先例）。

### L3. 注册必须携带设备类型/profile，否则解码链断裂
- DeviceHub `createDevice` 用 TB 默认 profile（动物追踪器），而胶囊/追踪器必须挂各自的 `*-OC-配置-v2` profile，否则网关解码与规则链不工作。
- 本次靠人工事后修正了 `64af` 的 profile。

### L4. "设备上行到不了 TB"的第一嫌疑是网关项目映射缺失
- 两台胶囊（NS project 148）和两台追踪器（project 217）上行静默的根因是 OC connector 没有这两个项目的 topic 映射，而非设备/网络问题。
- 该变更属项目级网关操作，需要审批、备份、重载、验证四步（本次已按此执行，备份存 `02-smart-livestock/.local/backups/oc-shared-20260917T1525Z.json`）。

### L5. 项目归属不能靠 EUI 前缀猜
- `00956906001264af/ef` 按前缀被当成停车设备，NS 里实际名字是"牛羊追踪器"。猜错会导致注册到错误的业务项目、消费组、数据链路全错。
- 权威归属来源是 NS（或设备台账），不是命名规律。

### L6. NS 状态字段不可单点信任，且"在线" ≠ 有有效上行
- 胶囊 `001a0102ff000644`：NS list API 返回 `f_cnt_up=0`，但 NS 详情页 UI 显示上行帧计数器=34 且有真实历史帧——**API 字段与 UI 口径不一致**，单一字段不能作为"设备从未上行"的证据。
- 该设备真实周期约 4 小时且不稳定（出现过 24 小时间隔），RSSI -103~-107 / SNR -6/-7 弱信号。
- 健康判定要区分四级：NS 已激活 → 有载荷上行 → TB 已解码 → 业务库已入库；每级的证据字段要标明口径来源（NS API / NS UI / TB / 业务库）。

### L7. 诊断必须感知设备上报周期
- 胶囊解码数据中 `dataSyncCycle=15`（15 分钟），用 10 分钟探针监听得出了"项目静默"的错误结论。
- 二次验证：644 的 NS 历史显示其有效周期约 4 小时且有 24 小时级别的间隔——`dataSyncCycle` 是设备参数，**观测到的真实周期**才是静默判定依据，两者可能相差一个数量级。
- 静默判定的窗口必须 ≥ 2 倍真实上报周期；上报周期应作为设备档案的一等属性（初始按类型默认，随后按历史帧间隔自学习）。

### L8. TB timeseries 查询会返回"伪影条目"
- 对不存在数据的 key 显式查询时，TB 返回 `{ts: 查询时刻, value: null}`，极易误判为"设备刚上报了空数据"。本次一度把伪影当成胶囊在上报。
- DeviceHub 回补通道实测已免疫（null 帧全部被跳过、未进 MQ），但该行为必须写进契约与排障文档。

### L9. 消费端首次启动的 offset 语义会回退业务状态
- parking 侧新 consumer group 以 `CONSUME_FROM_FIRST_OFFSET` 回放历史帧，两条本地从未见过的旧帧驱动状态机覆盖了车位当前状态。
- 已修为 `CONSUME_FROM_LAST_OFFSET`；但"旧帧在窗口期到达回退状态"的风险对任何回补通道都存在，业务端需要持久化高水位线。

### L10. 正向验证（做对了的事）
- 注册歧义拒绝、幂等注册（ALREADY_REGISTERED）、frameId 稳定哈希、双通道同帧零重复（parking 208 条 MATCHED_DUPLICATE、livestock `(device_id, report_time)` 零冲突）均按设计工作。
- 这些机制要保留并产品化，而不是只在代码里。

## 二、平台管理功能需求

### P0（本期即需要）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-01 | **设备接入预检（preflight）**：注册前一站式检查 NS 存在性与归属项目、OC 网关映射是否覆盖该 NS 项目、TB 是否已有同名/大小写变体设备、目标 profile 是否存在、本地绑定状态 | `GET /api/v1/devices/preflight?devEui=` 返回各项 PASS/FAIL + 修复建议；对 644/853 这类设备能直接指出"项目 148 无网关映射" |
| R-02 | **profile 感知注册**：注册接口接受 `deviceType`（或 `deviceProfileId`），平台维护 deviceType→TB profile 映射表；缺类型时拒绝创建而非用默认 profile | 注册胶囊自动挂 `瘤胃胶囊-OC-配置-v2`；不带类型且 TB 无现成设备时返回明确错误 |
| R-03 | **EUI 规范化与变体歧义检测**：EUI 一律小写入库；TB 查找覆盖大小写变体，发现变体即报歧义并列出所有候选 | 对 `00956906001264Af` 这类存量能检出并提示，不再静默新建 |
| R-04 | **重名设备治理视图**：reconcile 报告中的 `TB_IDENTITY_CONFLICT` 单独成表，附每台候选设备的遥测活跃度（有数据/空壳）、创建时间、建议保留方 | 运维能据此一键发起清理工单（删除动作仍需人工确认，平台不自动删） |
| R-05 | **设备健康四级视图**：NS 激活态 / 有上行 / TB 已解码 / 业务库已入库，逐级展示最后达到时间与卡点 | 健康端点或页面能区分 644（已激活但零上行）与 64ef（全链路通） |

### P1（紧随其後）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-06 | **上报周期感知**：设备档案记录 `expectedReportIntervalSeconds`（按 deviceType 默认 + 历史帧间隔自学习）；静默/掉线判定窗口 = max(2×周期, 5min)；健康端点按此标记 stale 而非固定阈值 | 胶囊 15 分钟周期不会在 16 分钟无帧时误报警，也不会 1 小时不报还不报警 |
| R-07 | **网关映射治理**：检测 NS 侧有活跃设备但 OC 无映射的项目清单（只读巡检）；映射变更走"备份→变更→重载→验证"工单流并留档 | 巡检报告能提前发现 148/217 这类缺口；每次变更自动生成备份文件与验证结论 |
| R-08 | **消费端保护规范产品化**：契约文档明确新 consumer group 必须用 LAST_OFFSET；平台在 topic 元数据中标注"可安全回放窗口"；业务端高水位线建议写入接入 checklist | 新接入方不再踩回放回退状态的坑 |
| R-09 | **TB 查询伪影免疫写入契约**：所有诊断/健康/预检功能过滤 null 值条目；契约文档记录"显式 keys 查询会返回 `{ts:now,value:null}` 伪影" | 排障文档可查；平台任何"最后上报时间"展示不受伪影污染 |
| R-10 | **通道可观测性增强**：channels/health 增加每设备游标滞后（按各自上报周期归一化）、null 帧计数、WS 订阅数与 ACTIVE 设备数一致性校验 | `/api/v1/channels/health` 能直接看出"订阅了 13 台但 ACTIVE 只有 8 台"这类不一致 |

### P2（二期，与命令下发/调度联动）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-11 | **设备台账统一视图**：DeviceHub `registered_devices` 扩展 NS project/app、deviceType、profile、上报周期、capabilities，成为跨项目设备事实源 | 注册时自动从 NS 校验归属项目，杜绝 L5 类归属错误 |
| R-12 | **下行命令前置检查**：命令下发前校验设备当前在线窗口（Class A 上行窗口）、profile 支持、网关 serverSideRpc 映射存在 | 对静默期设备下发命令时明确提示"将进入排队等待上行窗口"而非假成功 |

## 三、分期建议

- **P0 与灰度并行**：R-01~R-05 不改变现有数据链路，只增强注册与诊断，建议在灰度比对期内完成，用这 6 台设备做验收样本。
- **P1 跟随灰度收尾**：R-06~R-10 与"关闭单体旧通道"同步上线，作为灰度验收的一部分。
- **P2 并入命令下发/调度二期**：R-11/R-12 是二期设计的前置依赖。
