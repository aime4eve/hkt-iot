## 1. 寿命计算假设的扩展因子

我们理解您需要完整的"乘数链"以便自行核算。寿命计算的全部假设因子如下：

| 因子 | 取值 | 依据 |
|------|------|------|
| 标称容量 | 17,000 mAh | EVE ES-261520/W 规格书（ER26500×2 + SPC1520） |
| 高温降额 | ×0.85 → 14,450 mAh | 克罗地亚夏季沥青路面 60~70℃：ER26500 高温容量衰减 10~15%（EVE 数据）+ 电压截止不可用容量 5~10% |
| 年自放电 | 2%/年 | EVE 官方：ER26500+SPC1520 方案年自放电 <2%，保守取上限 |
| 停车事件裕量 | ×1.20 | 20% 反复停车裕量（覆盖误触发、传感器重试） |
| 迭代模型 | 逐年：剩余 = 上年剩余 − 年耗电 − 上年剩余×2% | 计及自放电随容量衰减的非线性 |

**公式：** 寿命（年）= 迭代至剩余容量 < 年耗电时停止，初始容量取 17,000（常温）或 14,450（85% 降额）。

## 3. ADR 行为（ADR_ACK_LIMIT / ADR_ACK_DELAY）

**参数归属：** ADR_ACK_LIMIT 和 ADR_ACK_DELAY 是 LoRaWAN MAC 层参数，由 MPS-100 的 LoRaWAN 模组（LSD4WN-2L817M90，利尔达）固件实现。**标准 LoRaWAN 默认值：ADR_ACK_LIMIT = 64，ADR_ACK_DELAY = 32**（即连续 64 帧未收 ACK 后置位 ADRACKReq，再等 32 帧确认）。我们将向利尔达确认该模组固件的实际值，3 个工作日内回复。

**链路恢复后是否降回低 SF：**

ADR 是双向机制，但**是否下调 SF 由网络服务器（NS）决定，不是设备单方面行为**：
- 设备端：连续未收 ACK 时逐步上调 SF（SF7→9→12），同时置位 ADRACKReq 通知 NS。
- NS 端：收到 ADRACKReq 后，若判定链路恢复，应下发 LinkADRReq 指令下调 SF。
- **因此：** 若您的 NS（ChirpStack / TTN / 自建）配置 ADR 策略，链路恢复后 NS 会主动下调 SF，设备随之降回；若 NS 不配 ADR，设备可能停留高 SF。

**建议：** 请确认您使用的 NS 及 ADR 配置，我们可协助优化，确保链路恢复后及时降回 SF7/9，最大化电池寿命。
