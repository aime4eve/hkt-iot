# iBeacon 信标扫描识别定制需求 · 技术评估

> 日期：2026-10-08 ｜ 状态：**评估完成；2026-10-08 拍板——我方供卡为商业主线（§9），客户自备卡降为兼容备选；待 OEM 卡询价/样验与 DA14531 源码落实**
> 性质：内部技术文档（含代码行号），不直接对外发送；对外答复口径见文末"客户答复策略"。
> 客户需求原文要点：
> 1. 地磁传感器扫描并接收 iBeacon 信标信号，经 LoRaWAN 上报平台；
> 2. 车辆停入车位时，通过蓝牙信标确认是否为授权人的车；
> 3. 只捕获 UUID 以 `564E4554`（ASCII "VNET"）开头的信标卡，过滤其他蓝牙干扰（固定字节过滤）；
> 4. 测量传感器与信标的距离，识别**最近**的信标并上传其信息；
> 5. 车辆激活传感器时才启动蓝牙扫描，以降低电池消耗；
> 6. 目的：平台确切知道"谁、用哪张卡、何时"停在车位上。客户愿意讨论定制方案及费用。

---

## 1. 结论

**需求可行，且不需要改硬件。** 整机已标配一颗低功耗蓝牙 SoC（Dialog/Renesas DA14531，BLE 5.1），当前固件仅用作手机配网透传桥。本定制 = 将其从"配网桥"升级为"事件触式的 iBeacon 扫描器"，LoRaWAN 链路与事件架构完全复用。客户设想的"车来才扫描省电"模式与现有事件驱动架构天然吻合。

定制工作量分三段：
| 段 | 仓库 | 规模 |
|---|---|---|
| DA14531 扫描固件（GAP Central + iBeacon 解析 + 过滤 + UART 协议） | 不在本仓库（Renesas SDK） | **大（NRE 大头）** |
| 传感器主控固件（扫描状态机 + TLV 扩展 + 参数配置） | 本仓库 | 中 |
| 平台解码器 + 卡号-人员映射 | HKT-Decoders | 小 |

## 3. 端到端设计

### 3.1 时序（利用现有 5s 防抖窗口）

```
车辆压上传感器
 → 磁力计+雷达判定"车来"（现有逻辑，约 2-3s）
 → park_process() 置事件标志（control_center.c:774 分支，现有）
 → [新增] 主控经 LPUART1 命令 DA14531 限时扫描（5-10s，与 park_delay 并行）
 → [新增] DA14531 回报最近一张 VNET 卡 → 结果暂存 → 并入事件帧 TLV
 → 事件帧 LoRaWAN 上行（现有路径）
 → 平台解码 → 卡号映射到人员/授权 → "谁、几点、哪个位"
全程约 15-20s（含 SF 慢速区域余量），停车业务可接受
```

- 事件期间主控本就处于唤醒态（`sleep_delay = WAIT_SLEEP_TIME_DELAY`），扫描不需要新唤醒机制。
- 扫描超时应作用于 `uartLoRa.sendDelay` / `park_delay` 的等待逻辑：扫描完成或超时，二者取先，才放行事件帧组装。
- 车辆**离开**事件是否扫描待客户确认（建议默认不扫，省电且离开时卡已随车走）。

### 3.2 DA14531 固件改造（NRE 大头）

- 增加 **GAP Central 扫描角色**：收到扫描命令后启动、限时、自动停止并恢复配网广播（时间片复用，扫描期间暂停 ADV）。
- **iBeacon 报文解析**：Apple 厂商数据（Company ID 0x004C + Type 0x02 + Length 0x15）→ 16B UUID + Major(2B) + Minor(2B) + Measured Power(1B)。
- **固定字节过滤**：UUID 前 4 字节 == `56 4E 45 54` 才收，其余广播全部丢弃——芯片侧硬过滤，不占主控资源；前缀可配置。
- **RSSI 聚合**：窗口内同一张卡取最强 RSSI（抗抖动），结束时上报最近 1 张（可选 top-N）：UUID + Major/Minor + RSSI + Measured Power。
- **本地命令协议**：与现有透传流量区分（建议 0xA5 起的帧头 + 命令/校验），命令集：启停扫描、参数（前缀/窗口）、结果上报。
- ⚠ **前置工程项**：DA14531 固件源码不在本仓库——需找回原开发档案或基于 Renesas DA145xx SDK 重写（须保留现有配网透传 + STM32 BLE OTA 路径 `Compents/BootLoader/main.c:65`）；-00000FX2 为无内置 flash 版本，产线烧录/现场升级方式待确认。**此项直接影响 NRE 报价，报价前必须落实。**

### 3.3 主控固件改造（本仓库）

| 改动点 | 位置 | 内容 |
|---|---|---|
| 扫描触发 | `control_center.c` 车来分支（774 行附近） | 事件时经 LPUART1 下扫描命令；管理扫描状态机（等待/超时 8-10s/重试 1 次） |
| 结果解析 | `communicate.c:715` fromBleDataHandle | 新增帧头分支，解析结果入 `beacon_result_t` 全局 |
| TLV 扩展 | `communicate.h:15-31` + `setDataPackage()` | 新增 `DATATYPE_DEVICE_BEACON = 0x87`：UUID 有效段(12B) + Major(2B) + Minor(2B) + RSSI(1B int8) + MeasuredPower(1B) = 1+18B |
| 帧组装 | `Device_PeriodicReport()` / 新事件帧函数 | 车来事件帧追加信标 TLV；**注意 `buffer[50]` 上限**（现 ~19B + 18B ≈ 37B，勿再塞非必要字段） |
| 参数配置 | flash + BLE 命令 + 平台下行 | UUID 前缀(4B)、扫描窗口(s)、功能开关；`DataType` 加下行配置类型 |
| 回归 | 三种 park_mode × 事件/周期上报 | 现有 89 项测试框架跑通 |

**字节预算**：上行省略固定前缀 `564E4554`（平台解码时补全），全帧 ≈ 5(hkt头) + 14(现有TLV) + 18(信标TLV) = **37B**，低于最差 DR（SF12，51B）上限。若某频段 DR0 更小或加报 top-N，再议压缩（如只报 UUID 后 8B）。

### 3.4 平台侧（HKT-Decoders）

- 解码器新增 0x87 TLV：补全前缀 → 完整 UUID/Major/Minor/RSSI 字段。
- **卡号→人员→授权映射放平台**（推荐）：传感器只报"看见哪张卡"，不做白名单——避免向现场设备分发密钥/名单，卡注销也无需碰现场设备。

## 4. 功耗

- DA14531 扫描 RX ≈ 5mA；按每天 20~50 次停车事件、每次 8s：**0.2~0.6 mAh/天**，相对电池容量可忽略；主控事件期本就唤醒，无额外唤醒开销。
- 现状 DA14531 常开广播（配网用）为既有底电流，扫描为增量。
- **上线前复测整机功耗出报告**（对照 `Docs/地埋式地磁功耗测试图.png` 基线）。

## 5. 风险与现实约束（对客户必须讲清）

1. **"测距"精度**：RSSI 只能折算米级粗略距离，受车身金属遮挡、卡片摆放影响大。实践判据 = **"信号最强的卡 = 本位车辆"**（邻位 ≥3m 间距时可靠）。建议验收线：卡固定于车内（如仪表台）正确识别 ≥95%、邻位误判 ≤5%，需样卡现场矩阵测试后定。
2. **地埋式 vs 表贴式**：2.4GHz 需穿井盖/沥青——金属井盖基本不可行，复合材料亦有明显衰减。**建议该功能绑定表贴式 MPS100 交付**；地埋式先实测穿透再承诺。
3. **信标卡规格未知**：广播间隔决定扫描窗口（1s 间隔卡需 5-10s 窗口），TX 功率影响覆盖。客户提"VNET 卡"大概率已有现成卡，需**要样卡**。
4. **DA14531 源码/烧录**（见 3.2 ⚠）。
5. **时延预期**：停车 → 平台获知卡号约 15-20s。

## 9. 主线方案（2026-10-08 拍板）：信标卡由我方供应

> 触发：商务讨论"卡是否也由我们提供"→ 拍板"供卡为商业利益最大化主线"。本章只列相对 §1-§8 的**修正项**，未提及内容一律沿用；商业逻辑见 §10。

### 9.1 核心变化：从"适配未知硬件"变为"端到端系统设计"

- 卡从外部约束（未知型号/间隔/功率，射频承诺全部挂"待样卡"）变为**我方设计自由度**：UUID 方案、广播间隔、TX 功率、形态、电池规格都可选可标定。
- 传感器侧（DA14531 扫描固件、主控状态机/TLV、解码器）**设计不变**；平台侧新增卡资产管理模块。
- 验收数据可**先在厂内自测**再对外承诺，PoC 不再依赖客户提供任何东西——销售周期缩短、承诺口径更有底气。

### 9.2 技术修正

1. **UUID 方案我方定义**：前缀保留可配置（若客户存量系统要求 `564E4554` 则照编；否则用我方命名空间）。建议编码：Major=客户/站点号，Minor=卡序号——发卡时即知映射，平台可自动建档。
2. **卡规格成为优化变量，首选带加速度触发广播的卡**（OEM 成品卡普遍支持）：
   - 静止（车停放/卡在钱包不动）→ 深度休眠（µA 级）；移动（车在开）→ 100ms 级快速广播；
   - 与"事件触发扫描"天然配对：车到达瞬间卡恰在高速广播 → **扫描窗口可从 5-10s 缩到 2-3s**、捕获率更高、时延更短；卡电池寿命同步大幅延长；
   - 这是"我方选卡"才能拿到的系统级优化，客户自备卡不一定有此特性。
3. **产线逐卡标定 Measured Power**（1m 参考 RSSI）并印 QR/序列号 → 距离折算与"最近卡"判定质量提升，发卡扫码即绑定。
4. 原 §5.3"信标卡规格未知"风险消除；§7 问题 1（索样卡）删除。

## 10. §10 商业逻辑与行动清单（2026-10-08 定案）

### 10.1 供卡为什么是商业利益最大化（六条）

1. **一次性买卖变年金流**：卡按用户/车卖（住户项目 M≈1.5-3× 车位数），电池 2-3 年到期形成换卡复购周期——传感器是一次性收入，卡是周期性收入。
2. **BOM 价差**：OEM 卡成本 $3-8（量价，以询价为准），含配置+QR+保修的方案卡售价可到 $12-25 区间（对齐市场零售卡价格带），单品毛利 $5-15，随项目量放大。
3. **NRE 定价弹性**：卡毛利可反哺 NRE——可用"低门槛 NRE + 卡略高价"结构降低客户签约阻力，把钱从一次性前置挪到长期回收。
4. **全链路责任 = 报价权**：客户自备卡时射频问题会变成"你的传感器不行/我的卡没问题的扯皮；两端都是我们的，才能对识别率做承诺、对承诺收溢价，交付风险可控。
5. **生态卡位**：发卡流程（QR/序列号台账+平台绑定）一旦成为客户运营习惯，后续卡采购自然回流；每张卡还是随车流动的品牌触点。
6. **升级路径即第二增长曲线**：D6 防克隆滚动 ID"安全卡"从技术备选升格为**付费高级版**候选——同时解决克隆风险（§9.4）与协议层锁定弱的短板（见 10.2）。

### 10.2 必须正视的一个短板：协议层锁定弱

标准 iBeacon 的 UUID 是明文公开格式——**任何知道前缀的第三方都能卖"兼容卡"**，客户理论上可绕开我们采购。真实的护城河不在空口协议，而在三层：
- **发卡运营绑定**：卡序列号台账+平台绑定+保修政策（运营锁定，软）；
- **安全卡（D6）**：滚动加密 ID 须我方 DA14531 固件解密——**唯一的技术性锁定**，若该客户场景付费意愿高，应作为二期主推而非可有可无；
- **整机套餐定价**：传感器+卡+平台整体打包让"单买兼容卡"省不了多少钱（商务锁定）。
