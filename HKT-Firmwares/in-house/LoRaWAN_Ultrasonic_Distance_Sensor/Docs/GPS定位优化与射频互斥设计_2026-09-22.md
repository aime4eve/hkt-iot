## 1. 背景与根因（摘要）

真机 `00956906000de956` 三天 NS 数据（640 帧上行）归因结论：

1. **GPS 全零率 86%（473/548）主因：每个定位窗口对 GNSS 硬断电 + 90 秒预算，与冷启动定位时间冲突。** 失败窗口经帧间隔分位证明真实满跑 90 秒（非睡眠杀死）；成功游程 1.5~4h 与星历有效期吻合（模组有备份电源，热定位秒出）；冷启动在该点位普遍超 90 秒。
2. **独立问题：确认上行拿不到 ACK → 固件无间隔立即重发 → 连续 5 次失败即强制重入网。** 2.8 天 29 次软重入网（应用序号跨会话连续，铁证），风暴期（09-21 14:39 起）与 GPS 100% 失败期重合。网关下行已验证正常（29 次 Join-Accept 全部收到），矛盾集中在**模组数据接收窗/确认配置**，属开放问题（§10.1）。
3. **重叠放大：** 冷启动时入网发射风暴与 GPS 窗口同开（开机必现：`flash.c:405` 置 joinEvent=INIT 与 `gps_stamp` 零初值同时触发）；重发风暴的发射持续压制本就吃紧的冷启动窗口。

## 3. 改动一：GPS 与 LoRaWAN 射频互斥

### 3.1 现状缺陷（代码位置）

- 主循环单线程轮询（`main.c:60-69`），GPS 与 LoRaWAN 各自按独立时间闹钟触发，互不感知：
  - GPS：`gps_stamp <= Timestamp` 即上电找星（`gps.c:376-382`），最长 90s，期间用 `sleep_delay` 钉住系统不睡；
  - LoRaWAN：入网（`LoRaWAN_JOINEVENT_REGISTER` 最长 120s 发射风暴）与上行（`sendLoRaWANData` 单次阻塞最长 ~22s：busy 等 15s + stat 等 6s+1s）。
- 开机必现重叠：`FLASH_Read_Param` 在 `power_on=1` 时置 `joinEvent=INIT`（`flash.c:405-407`），`gps_stamp` 零初值 ≤ `Timestamp`，首个 500ms 轮询即开 GPS 窗。
- 服务器时间同步/GPS 周期下发均置 `gps_stamp = Timestamp`（`communicate.c:361/385`）→ 立即开窗，而此刻模组刚做完一轮收发。
- MCU 醒着期间 LoRaWAN 模组保持唤醒（仅整机睡眠时才睡，`control_center.c:67-68`），GPS 90s 窗口内模组空耗。

### 3.2 设计规则（互斥闸门）

新增互斥标志 `device_t.gps_acquiring`（定位窗口进行中）。四条规则：

1. **开窗闸门**：到点开窗时，若 LoRa 射频忙（`joinEvent != IDLE` 或 `uartLoRa.sendDelay != 0`）→ 顺延 `GPS_DEFER_SEC`（30s）再试。**闸门只看这两个必然自行归零的条件**（入网 ≤120s、sendDelay 1ms 递减 ≤3s）；明确不含"待发队列非空"——未入网时队列积压是常态且不解除，含它会让 GPS 永久饿死。发送失败路径不置 sendDelay 的缺陷由改动三补上，两个条件合起来覆盖全部路径。
2. **模组入睡**：闸门放行后，复用整机睡眠路径同一对调用 `setLoRaWANStatus(LoRaWAN_SLEEP_STATUS)` 让模组在 GPS 窗口内睡眠（Class A 下无待发上行则无 RX 窗口，安全；`sendLoRaWANData` 自带按需唤醒，`communicate.c:183-184`，量产验证过的路径）。
3. **发送闸门**：`DeviceStateProcess` 发送分支增加 `!device_t.gps_acquiring` —— 定位窗口内不发射，数据留在 lwrb 队列，关窗后同分支自然发出。
4. **入网让路（中止路径）**：窗口内若 `joinEvent != IDLE`（按键重入网 `control_center.c:119`、下行恢复出厂 `communicate.c:334`、BLE 命令均可触发）→ 立即中止本次定位：GPS 关电、清标志、`gps_stamp = Timestamp + GPS_ABORT_RETRY_SEC`（300s）后重试；**不上报、保留旧位置**（与超时路径上报 (0,0) 的语义差异是有意设计：入网是主动让路，服务器继续看上次位置即可；如需感知失败可改为上报 (0,0)，留裁决）。得益于主循环顺序 `LoRaWAN_JoinInit → Gps_Handler`，中止在同一圈循环内生效，早于模组复位完成（205ms），Join-Request 实际不会落进 GPS 窗口。

### 3.3 具体修改点

**(a) `USER/Drive/include/control_center.h`** — `struct device` 位域区（`:30` `gps_state` 旁）新增：

```c

```

**(b) `USER/config.h`** — 新增：

```c

#define GPS_DEFER_SEC          30    // 射频忙时定位顺延（秒）
#define GPS_ABORT_RETRY_SEC    300   // 入网让路中止后的重试间隔（秒）
```

**(c) `USER/Drive/gps.c`** — 顶部补 `#include "LoRaWAN_APPLY.h"`（枚举、`extern struct LoRaParam LoRaWAN`、`setLoRaWANStatus` 声明所在）。

### 3.4 时序正确性论证

- **无竞态**：单线程 + 主循环顺序固定（`Gps_Handler` 先于 `DeviceStateProcess`）——GPS 开窗当圈即置标志，发送闸门同圈生效；入网触发当圈 `Gps_Handler` 随后即中止。
- **RX 窗口边沿**：sendDelay=3s vs SF12 下 RX2 闭合 ≈3.3s 的 0.3s 边沿，与现有整机睡眠逻辑（同样在 sendDelay==0 时睡模组）同源同时序，不新增风险类别；闸门 30s 顺延粒度天然留足余量。
- **明确不改**：`fromLoRaWANDataHandle` 的 ACK 直发路径（Class A 下 GPS 窗口内模组已睡、无 RX 窗口，到不了那里；万一到了，应答服务器优先于定位）。
- **BLE 模式**：BLE 已连接时 GPS 常开分支 `wait_result_count==0`，不受发送闸门影响；调度开窗在 BLE 模式同样受限（≤窗口时长），可接受。
- **看门狗**：不新增阻塞；IWDG ≈20s、Stop 模式冻结，主循环每圈喂狗，不变。

### 3.5 残余风险

- ACK 直发路径理论上可在 GPS 窗口内发射（Class A 概率≈0，选择不闸，见上）。
- 最坏情况定位时刻漂移 ±30s（对 ≥10min 定位间隔无感）。
- 中止路径不上报位置（服务器无感知），语义与超时路径不同——已留裁决点。

## 4. 改动二：定位窗口预算 90s → 240s

### 4.1 动机与依据

失败窗口全部是真实满跑 90s 的冷启动超时；成功游程证明"给够时间就能定"。冷启动在边际天空视界下需要 120~300s，240s 覆盖大部分场景；成功窗口靠"有定位即提前关窗"不受影响（热定位秒级关闭）。

### 4.2 具体修改点

**`USER/config.h`**：

```c
#define GPS_COLD_WAIT_TICKS    480   // 定位窗口预算（×500ms）；180=原值90s，480=240s
#define GPS_FIRSTFIX_FLOOR_TICKS  (GPS_COLD_WAIT_TICKS - 20)  // 原160等比
#define GPS_FIRSTFIX_CLEAR_TICKS  (GPS_COLD_WAIT_TICKS - 40)  // 原140等比
```

**`USER/Drive/gps.c`**：

1. `static u8 wait_result_count;` → **`static u16`**（u8 上限 255 tick = 127.5s，装不下 480）；
2. `wait_result_count = 180;` → `= GPS_COLD_WAIT_TICKS;`
3. 热启动首定位逻辑中两处常量 `160`/`140`（原 `gps.c:399/406`）→ 换用上面两个宏，保持"首定位成功后延时 15s 关闭"的相对时序（30 tick 收尾保持不变）。

### 4.3 醒机红线（强制配套，不可省）

`unsleepTime > 300s` 触发强制重启（`control_center.c:59-61`，每醒机秒 +1，仅睡眠入口和 BLE 连接清零）。**窗口延长到 240s 后，入网（120s）+窗口（240s）+上报的连续醒时约 392s，不清零必然在窗口中途触发重启**。因此改动一的开窗代码中 `unsleepTime = 0;` 为强制项（自开窗起最坏 240+10+3+6 ≈ 259s < 300s ✓；入网期间 GPS 被中止/顺延，不并发）。

### 4.4 功耗影响

- 每个失败窗口多耗 (240-90)s × GNSS 捕获电流（L76K 约 35mA）≈ **+1.46mAh**；
- 最坏全失败、GPS 周期 10min：+8.8mAh/h——**建议现场 GPS 周期 ≥30~60min**（改动生效后成功率提升，失败窗占比大幅下降，实际增量远低于此上限）；
- 对冲项：窗口内 LoRa 模组入睡（改动一）省模组待机电流。

## 5. 改动三：发送失败退避与重入网阈值加严

### 5.1 现状缺陷

- `sendLoRaWANData` 失败路径**不置 sendDelay** → 立即重发（`communicate.c:199-236`）；ACK 应答路径失败同样（`:297-315`）。数据重新入队 + 下一圈主循环即再发，形成每帧 5~22s 的连续阻塞风暴。
- 连续 5 次失败即强制重入网（`:227-234`、`:306-313`），叠加 30min 入网退避梯子 → 实测 ~33min 一轮的"失败→重入网"循环（2.8 天 29 次）。

### 5.2 具体修改点

**`USER/config.h`**：

```c
#define SEND_FAIL_BACKOFF_ENABLE 1
#define SEND_FAIL_BACKOFF_SEC    10    // 发送失败后的重发间隔
#define SEND_FAIL_REJOIN_CNT     10    // 连续失败多少次才强制重入网（原5）
```

**`USER/Drive/communicate.c`**：两处失败路径（`:203` 与 `:301` 的 `if (getLoRaWANSendStat())` 进入失败分支后、return 前）加：

```c
#if SEND_FAIL_BACKOFF_ENABLE
        uartLoRa.sendDelay = SEND_FAIL_BACKOFF_SEC * SEC_DELAY;
#endif
```

两处阈值 `device_t.send_fail_cnt >= 5` → `>= SEND_FAIL_REJOIN_CNT`。

### 5.3 影响与风险

- 真实断网的判定时延从 ~2min 变 ~5min（10 次 × (10s 退避 + 模组内部重试)），入网退避梯子不变——可接受；
- 单次失败退避 10s 期间系统不睡（sendDelay 非零阻塞睡眠）——比现状的连续风暴总醒时更短；
- **注意**：此改动不解决"为什么拿不到 ACK"（开放问题 §10.1），只止血风暴。根因解决后阈值可回调。

## 6. 改动四：GNSS 星座配置下发（默认关闭）

### 6.1 现状

`set_gps_galaxy()` 从未被调用，且其底层 `nmea_write` 的实际发送语句被注释（`gps.c:50`）——固件从未给 L76K 下发过任何配置，模组按出厂默认星座运行。若默认不含北斗，国内点位可见星数打折。

### 6.2 具体修改点

1. `gps.c:50` 解注释 `Gps_SendData((u8 *)session->msgbuf, session->msgbuflen);`；
2. 开窗后延迟下发（模组上电启动 ~1s）：开窗处置 `galaxy_pending = 2`，在 `wait_result_count` 分支每 500ms 递减，减到 0 时调用一次 `set_gps_galaxy(GPS_GALAXY_VALUE)` 并清零；
3. `config.h`：

```c
#define GPS_GALAXY_CONFIG_ENABLE 0    // 待 L76K 手册确认 PCAS04 取值后置 1
#define GPS_GALAXY_VALUE        3     // $PCAS04 模板现值，语义待手册核实
```

### 6.3 前置条件（阻塞项）

**必须先查 L76K AT 手册确认 `$PCAS04` 各取值的星座组合**（模板值 3 的含义未核实）。若模组默认已含北斗则本改动无收益，保持宏为 0 即可。每次开窗都断电重上电，配置每窗发一次（PCAS 配置掉电不保存，如手册支持 `$PCAS00` 保存可改为仅首窗下发）。

## 7. 改动零（前提）：构建频段修正

### 8.3 验收用数据分析方法

复用诊断方法（详见诊断报告）：应用层 seq（帧字节 4）与 LoRaWAN FCnt 分离统计——seq 连续+FCnt 归零=软重入网，seq 归零=整机重启；GPS 帧间隔分位数判定窗口行为；有效坐标游程长度对照星历有效期。

## 9. 回滚方案

- 单项回滚：`config.h` 宏开关（`GPS_LORA_MUTEX_ENABLE=0`、`GPS_COLD_WAIT_TICKS=180`、`SEND_FAIL_BACKOFF_ENABLE=0`、`GPS_GALAXY_CONFIG_ENABLE` 保持 0）；u16 类型改动与 180 兼容，回滚无需改类型；
- 整体回滚：revert 提交；所有改动不涉及协议帧格式与 Flash 参数布局，新旧固件可无缝互换。

## 10. 开开问题（本设计范围外，需闭环）

1. **模组数据 ACK 接收核查（根因 2 的另一半）**：上行 NS 全收到、29 次 Join-Accept 全收到，唯独数据帧 ACK 模组收不到/不认。嫌疑：`AT_LoRaWAN_setConfirm(1,3)` 参数语义、`AT_LoRaWAN_setRX2(0,869525000)` 参数含义、`AT_LoRaWAN_setFREQ(1,3,868100000)` 三信道子带与 NS 下行计划的匹配——对照 `Docs/` 下 LSD4WN-2L817M90 EU868 规格书逐条核实，配合设备串口日志（"LoRa SendData Fail"频率）与 NS 下行日志定案。
2. **L76K 备份电源硬件确认**：对照 `Docs/SCH_垃圾桶满溢检测传感器_V2.0` 原理图确认 VBAT_BACKUP 是否有备份电池/法拉电容——决定热启动语义与窗口策略调优方向（§4 与 §6 均相关）。
3. **config.h 频段漂移管理**：仓库配置（US915）与在售批次（EU868）不一致的来源梳理，建议按批次固化配置或引入构建profile。
4. **中止路径上报语义**：保留旧位置（本设计默认）vs 上报 (0,0)（与超时路径一致），待裁决。

## 附录 B：设计取舍记录（对敲结论）

1. GPS 起始闸门**不含**"待发队列非空"（未入网时队列积压不解除 → GPS 饿死）；
2. 发送失败路径补 sendDelay 后，闸门两条件覆盖全部射频活跃路径；
3. 中止走 GPS 让路而非入网让路（入网优先级高；单线程顺序保证中止先于首个 Join-Request）；
4. 模组入睡复用整机睡眠同一对调用，不引入新硬件假设；
5. `unsleepTime` 在开窗清零为改动二的强制配套（否则 392s 连续醒时撞 300s 红线）；
6. RX2-SF12 3.3s vs sendDelay 3s 的 0.3s 边沿沿袭现有睡眠逻辑，不单独加固。
