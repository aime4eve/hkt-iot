# 固件缺陷台账

in-house 固件工程的缺陷记录。发现方登记缺陷（现象 + 根因源码行号 + 影响版本），固件组修复后回填修复版本并更新状态。

## 记录约定

- **ID**：`FD-NNN` 全局流水号。
- **状态**：`OPEN`（待修）→ `FIXED`（已修复，注明版本）→ 亦可判 `BY-DESIGN` / `WONTFIX`（写明理由）。
- **每条必填**：现象、根因（`文件:行号`）、影响版本范围、修复建议；修复后补验证方式与日期。
- **严重度**：高=现网数据/功能错误且无绕行；中=有绕行或影响面窄；低=边缘场景。

## 明细

### SVC100（LoRaWAN_Solenoid_Valve_Controller）

#### FD-001 · 0x03 实时任务脉冲 3B 超读

- **提出**：2026-09-06（iOS 联调；下发脉冲 100，设备实得约 25787）
- **现象**：实时任务实际生效的脉冲计数 = `(下发值 << 8) | CRC高字节`。
- **根因**：`data[5]==7 && data[6]==3` 分支按 3B 读脉冲（`srcHex[5]<<16|srcHex[6]<<8|srcHex[7]`），第 3 字节实为帧 CRC 高位。两处：BLE 入口 `SVC communicate.c:1660`、共享分发 `communicate.c:556`。
- **修复**：2026-09-09 两处均改为 2B 读（`srcHex[5]<<8|srcHex[6]`），len 门槛保持 7（勿改为 8，会使现网安卓帧整体被拒）。
- **验证**：随下一版固件发布后，下发脉冲 100，设备实际计数应为 100。调用方帧格式不变（6B 载荷、len 7）。

### UDS100（LoRaWAN_Ultrasonic_Distance_Sensor）

#### FD-002 · hkt 0x06 对时帧死代码（与 DC200 家族同源）

- **提出**：2026-09-11（协议审计）
- **现象**：按安卓同款 hkt 0x06 对时帧发送，设备无 ACK、时间不生效。
- **根因**：0x06 分支的内层守卫 `data[5]==4 && data[6]==6` 嵌套在外层 `data[5]==5||9`（UDS `communicate.c:1183` vs `:1280`）之内被遮蔽，帧永远无法到达该分支。
- **影响**：hkt 对时在 UDS100/DC200 家族不可用。调用方现状：UDS100 改走 ASCII `syncDeviceTimestamp:<unix>`（无 ACK、固定 UTC+8，`communicate.c:1093`）；DC200 因 FD-003 直接禁用对时。
- **修复建议**：放宽外层门禁，或将 0x06 分支提级到与 0xFF 查询同层。

#### FD-004 · 写命令与 1Hz 查询在 RX 单缓冲互相挤撞（无 ACK 静默丢失）

- **提出**：2026-09-20（iOS 联调，通信日志取证）
- **现象**：写命令（0x02 配置 / 0xFE 开关机 / 0xFD 校准）紧邻查询应答窗口发送时被整帧丢弃——设备无 ACK、无动作；稍后重发同一帧即成功。实测：UDS100 开机首击失败 ×2 轮、0xFD 校准命令首次常丢。
- **根因**：RX 单缓冲 + 50ms 空闲判帧（`uart.c:315`），且查询处理阻塞数百毫秒（UDS 查询回调含测距/ADC）。1Hz 轮询节奏下，写帧极易与未消费完的缓冲拼接，仅最前帧被分发。
- **影响**：全部写类命令可靠性下降。调用方现状：发送写命令期间已暂停轮询规避。
- **修复建议**：RX 按 SYNC_HEAD 分段分发（而非整缓冲覆盖），或写命令入队主循环延迟处理；修复后调用方可恢复随写随查。
- **Android 补充实证（2026-09-22，V6.0.0b1 harness）**：UDS100/EPS100 真机 0x02 同现象；调用方写前静默 ≥1.2s（suspend 轮询 + 等在途查询处理完毕）即消除，UDS/EPS 0x02 全部 ACK 且读回一致。

### DC200 家族（LoRaWAN_ParkingSensor：MPS100 / EPS100）

#### FD-003 · ASCII 对时月份 +1

- **提出**：2026-09-11（协议审计）
- **现象**：ASCII 对时后设备月份比实际快 1 个月。
- **根因**：ASCII 对时路径写入 `tm_mon+1`（`DC communicate.c:1014`）；服务器同步路径（`:994`）的写法正确，仅 BLE ASCII 路径多加。
- **影响**：DC200 家族 BLE 对时不可用。调用方现状：对时功能已禁用。
- **修复建议**：对齐 `:994` 的服务器同步路径写法。

#### FD-005 · 开关控制模式下阀状态位（0x3C）恒 0

- **提出**：2026-09-22（Android V6.0.0b1 harness 真机验证，SVC100_0D26CF v13.14）
- **现象**：`port_mode` 设为开关控制（bit=1，如 0x03）后，0x03 实时任务开/关阀命令回 ACK 且 GPIO 动作序列执行（boost 上电、阀驱动输出），但轮询 0x3C 设备状态里的阀状态位（value1_state/value2_state）恒 0——App 阀状态卡片无法反映真实阀态。PWM 模式下状态位正常。
- **根因**：`gpio.c` 开/关阀执行函数的状态置位条件 `if ((device_t.port_mode & 0x01) != 1) device_t.value1_state = 1/0`（正向 ~:905、反向 ~:810）——**仅 PWM（脉冲）模式更新状态位，开关控制模式漏写**。
- **影响版本**：SVC100 全版本（源码同版本；开关控制模式现场必现）。
- **严重度**：中（阀动作本身正常；显示失真，绕行=使用 PWM 模式）。
- **修复建议**：状态置位按阀驱动方式分别覆盖开关/PWM 两模式，或统一由 `real_time_task_t.is_start/state` 反映。
- **验证方式**：port_mode=0x01 下 0x03 开阀（dur=30），轮询 0x3C 阀 1 应=1；回位后=0。

#### FD-006 · UDS100 设备配置现值越界（上报周期 3min）且合法同值回写被拒

- **提出**：2026-09-22（Android V6.0.0b1 harness 真机验证，UDS100_0DEA40 v2.10）
- **现象**：轮询 0x86 上报周期=3min，违反固件自身校验规则（0 或 10–1440）；按同值（3min）回写被静默拒绝——固件校验活着，说明越界值是历史写入遗留。
- **根因待查**：越界值来源（旧版本固件 0x02 入口无校验，或其它写入通道）；当前 v2.10 的 0x02 入口校验存在（合法化回写 ACK 实证）。
- **影响**：单台设备功能可用但违反承诺范围；用户想"原样保存"会被拒（需顺带改成合法值）。
- **状态**：该设备越界状态已借配置验证写入合法值（30min）消除。根因待查：若旧版固件入口确实无校验，建议核对其余字段是否存在同类越界遗留。

#### FD-007 · 0x03 busy 守卫解引用 current 前的空指针检查被注释

- **提出**：2026-09-22（Android V6.0.0b1 harness 真机验证，源码核对）
- **现象/风险**：`SVC communicate.c:1651` 生效守卫为 `local_schedule_t.current->is_start != 1`，其上一行被注释的旧守卫包含 `&& !local_schedule_t.current` 空指针检查。若调度器保证 current 恒指向常驻槽位则安全，否则无任务时为野指针读。
- **严重度**：低（防御性；实测无任务时 0x03 正常 ACK，说明当前实现下 current 非空）。
- **建议**：确认 `local_schedule_t.current` 生命周期；或恢复空指针守卫。

### UDS100（LoRaWAN_Ultrasonic_Distance_Sensor）

#### FD-008 · GPS 与 LoRaWAN 射频无互斥 + 定位窗口预算不足（户外全零率 86%）

- **提出**：2026-09-22（真机 00956906000de956 三天 NS 数据归因，长沙户外 EU868）
- **现象**：GPS 帧全零率 86%（473/548），有效定位仅 13.7% 且按小时簇状分布（白天 10-19 点 132 帧全败）；失败窗口经帧间隔分位证明真实满跑 90s。
- **根因**：
  1. 每定位窗口对 GNSS 硬断电（`USER/Drive/gps.c:411`），下窗冷启动，90s 预算（`:380` wait_result_count=180×500ms）在该点位天空视界下普遍不足；成功游程 1.5~4h 与星历有效期吻合（模组有备份电源，热定位秒级）。
  2. 射频无互斥：开机入网风暴与 GPS 窗口同开（`USER/Drive/flash.c:405-407` 置 joinEvent=INIT + gps_stamp 零初值）；周期上报/时间同步后立即开窗（`USER/Drive/communicate.c:361/385`）可与找星窗口重叠。
- **影响**：GPS 定位功能户外基本不可用；重发风暴期（见 FD-009）100% 失败。
- **修复建议**：见 `in-house/LoRaWAN_Ultrasonic_Distance_Sensor/Docs/GPS定位优化与射频互斥设计_2026-09-22.md` 改动一（互斥闸门）+ 改动二（窗口 90→240s，注意 wait_result_count u8→u16 与 unsleepTime 开窗清零强制配套）。
- **验证方式**：同点位 A/B ≥48h，成功率 13.7%→>80%，白天时段接近全天均值。

#### FD-009 · 发送失败无退避立即重发 + 连续 5 次即强制重入网（~33min 风暴循环）

- **提出**：2026-09-22（同一真机数据：2.8 天 29 次软重入网，应用 seq 跨会话连续铁证；风暴期序号几乎不涨）
- **现象**：确认上行被模组判失败后固件立即重发（无 sendDelay），连续 5 次即强制重入网 + 30min 退避梯子 → 实测 ~33min 一轮"失败→重入网"循环；同帧字节级重复上行（fcnt 89/92 同载荷）实证。网关/NS 下行已验证正常（29 次 Join-Accept 全收到），ACK 收不到的矛盾集中在模组数据接收窗/确认配置（AT+CONF=1,3 / AT+RX2 / AT+FREQ=1,3,868100000），为独立开放问题。
- **根因**：`USER/Drive/communicate.c:203-236`（sendLoRaWANData 失败路径不置 sendDelay、重入队即重发）与 `:227-234`、`:306-313`（5 次阈值）两处；ACK 应答路径 `:297-315` 同款。
- **影响**：空口风暴（费电+占空比浪费）、会话频繁重建（FCnt 清零）、入网发射持续压制 GPS 冷启动窗口（与 FD-008 叠加）。
- **修复建议**：设计文档改动三（失败退避 10s + 阈值 5→10）；模组 ACK 接收核查另列开放问题（设计文档 §10.1，对照 Docs/ 下 LSD4WN-2L817M90 规格书）。
- **验证方式**：稳定网关下重入网 ≤1 次/天；设备日志 "LoRa SendData Fail" 频次与 NS 下行日志对齐定案 ACK 根因。

#### FD-010 · GNSS 星座配置死代码

- **提出**：2026-09-22（源码核对）
- **根因**：`USER/Drive/gps.c:54` `set_gps_galaxy()` 无任何调用方；`:50` `nmea_write` 内实际发送语句 `Gps_SendData(...)` 被注释——固件从未向 L76K 下发星座/模式配置，模组纯按出厂默认运行，国内点位若默认不含北斗则可见星数打折。
- **影响**：边际天空视界下定位时间进一步拉长（与 FD-008 叠加）。
- **修复建议**：设计文档改动四（解注释发送 + 开窗后延迟下发一次），**前置条件：查 L76K AT 手册确认 $PCAS04 取值语义**（模板值 3 未核实），宏默认关闭。
- **验证方式**：串口日志确认模块 NMEA 输出含 BDS 句型（如 BDRMC/BDGSV），同点位定位成功率对比。
