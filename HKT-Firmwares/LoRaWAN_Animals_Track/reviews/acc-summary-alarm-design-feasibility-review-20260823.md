# `acc-summary-alarm-design.md` 可落地性评审意见

- 评审对象：`Docs/acc-summary-alarm-design.md`，版本 V1.2，日期 2026-08-20
- 评审日期：2026-08-23
- 评审方式：设计文档逐节评审，并对照当前工程源码、链接 map 与现有驱动实现
- 评审结论：**有条件可落地，但 V1.2 不建议直接作为开工基线**。核心算法和总体分层合理，真正风险集中在传感器配置语义、低功耗唤醒、异步通信路径和统计边界条件。

## 总体结论

该设计选择的“本地在线统计 + 摘要上报 + 独立事件告警”方向正确，不需要保存原始波形，符合客户需求。文档也已经识别出 Stop 前 ACC 关闭、LoRa 阻塞、量程饱和和 FIFO overrun 等关键差距。

不过，当前 V1.2 仍存在若干实现前必须闭环的问题：`0xB2` 配置字段不能表达低功耗双采样率，低功耗运动唤醒的硬件语义不足，LIS3DH 当前驱动与统计前置条件不匹配，Class C 切换仍可能引入阻塞，长统计窗口存在累加器溢出风险。建议先修订为 V1.3，再进入实现。

## 阻断项

### P0-1 采样配置协议不完整

设计允许两个采样率：

- 低功耗模式默认 `1 Hz`，允许 `1/10 Hz`
- 运动后采样率允许 `10/25/50 Hz`

但 `0xB2` 下行帧和 Flash 结构中只有一个 `sampling_rate_hz` 字段，无法同时保存稀疏采样率与运动后高频采样率。配置表与存储结构因此不一致。

**修改建议**：将字段拆为 `low_power_sampling_rate_hz` 与 `active_sampling_rate_hz`，并同步修改 `0xB2`、`0xB3`、Flash 结构、默认值和参数校验。

### P0-2 低功耗运动唤醒设计不足

设计只写了“启用 LIS3DH 硬件运动中断”，但没有定义：

- 硬件唤醒阈值、持续时间、锁存和 AOI 组合逻辑
- FIFO watermark 中断与运动事件中断同时路由到 INT1 时的区分方式
- 1 Hz 稀疏采样下 watermark 的具体配置
- 硬件中断与 `dynamic_magnitude >= alarm_threshold` 软件告警判定的关系

当前硬件只配置了 PB7 上升沿 EXTI。若低功耗 1 Hz 模式仍按 25 级 FIFO watermark 唤醒，MCU 约 25 秒才处理一次 FIFO，运动后提升到 25 Hz 的时效无法保证；若 watermark 配得较小，又可能失去低功耗效果。

**修改建议**：为低功耗模式明确 INT1 路由和中断复用策略。建议 FIFO watermark 和运动唤醒分时配置，或确认硬件可将不同事件路由到 INT1/INT2。硬件中断只用于唤醒和进入高频采样，告警仍必须由连续采样后的软件防抖确认。

### P0-3 原始幅值统计缺少传感器前置条件

设计要求原始合成幅值 `sqrt(x^2 + y^2 + z^2)`，静止时接近 `1g`。但当前非 FIFO 活动路径启用了 LIS3DH 高通滤波。若继续开启 HPF，静止合成幅值会趋近 0，`abs(magnitude - 1g)` 的活动分类将失效。

此外，设计要求一次寄存器地址自动递增批量读取 FIFO，但当前 `lis3dh_get_raw_data_fifo()` 是逐样本读 6 字节，并非一次批量传输。当前代码还使用 collect 型 FIFO 配置，连续采集应使用 stream 模式，避免 overrun 后停止收集。

当前 `lis3dh_set_mode()` 在配置写入后固定返回 `false`，这将导致设计中的“传感器配置失败保持旧配置”无法实现，所有配置都会被误判失败。

**修改建议**：文档明确连续统计模式必须关闭 HPF、启用 FIFO stream、读取原始样本而非 float 样本；驱动先修复返回值和批量读接口，再实现配置读回验证。

## 高风险项

### P1-1 Class C 切换也必须异步化

设计只要求 LoRa 数据发送流程非阻塞，但告警成功后打开 Class C 会调用现有 `AT_LoRaWAN_setClass()`。该函数最多重试 3 次，每次等待 1.5 秒并额外延迟 1 秒，最坏可阻塞约 7.5 秒。

25 Hz 下 LIS3DH FIFO 32 级约 1.28 秒充满。如果 Class C 切换在主循环中阻塞，ACC FIFO 必然 overrun。

**修改建议**：将 Class C 打开、读回确认、窗口计时、恢复 Class A 全部纳入同一个异步通信状态机，不允许任何 AT 等待路径阻塞主循环。

### P1-2 长统计窗口下累加器溢出

`acc_stats_t.magnitude_sum_mg` 使用 `uint32_t`。在 25 Hz、±4g、1440 分钟窗口下，累加值理论上可达约 `86,400,000,000 mg`，明显超过 32 位无符号数范围。

当前平台运行配置允许上报间隔最大 1440 分钟，因此这不是不可能配置，而是协议允许的边界状态。

**修改建议**：优先使用 64 位累加器；若 RAM 受限，可使用 48 位压缩累加或分段求均值，并显式限制“采样率 × 量程 × 窗口时长”组合。文档需要给出溢出证明和选型结果。

### P1-3 时间与覆盖率边界未闭环

当前 `get_syspant_ms()` 在超过 86400000 后直接清零。防抖持续时间、静默期和统计窗口到期若直接比较时间差，会在跨零点时出错。

低功耗模式在 1 Hz 与 25 Hz 间切换时，`expected_samples` 也不能用“整窗时长 × 当前采样率”计算，必须按每段配置频率对时间积分。

**修改建议**：统一提供单调毫秒计时或安全的时间差函数；`expected_samples` 在采样率切换时立即结算并累加。测试计划增加毫秒计时跨零和采样率切换用例。

### P1-4 Class A/C 会话恢复缺少模组行为验证

设计要求 Stop 前保存 LoRaWAN 会话状态，事件唤醒后不得默认重新入网。但当前 Stop 前会清除 `joinState` 并让模组睡眠，唤醒路径会触发重新初始化。设计没有定义如何确认模组睡眠后仍保有会话，也没有定义“明确失去会话”的判据。

**修改建议**：先做模组 POC：睡眠、唤醒、读取网络/Class/入网状态、透传切换耗时、会话是否保留。基于 POC 定义状态检查命令和失败回退路径。

## 中风险项

### P2-1 告警帧缺少触发时间

第 6 章要求缓存事件触发时间，但 `0xB1` 只上报事件序号、flags 和峰值。延迟补报时，平台无法还原事件发生时刻，只能依赖接收时间。

**修改建议**：增加事件 UTC 时间戳，或相对本次上行的分钟偏移；同时明确时间未同步时的无效值语义。

### P2-2 发送成功与网络恢复定义不足

设计中的“告警上行成功”和“网络恢复”需要可验证判据。现有状态脚可能只表示模组发送流程完成，不一定等价于 LoRaWAN 确认上行或平台应用层接收成功。网络失败后的 30 分钟重连退避也与“5 分钟内高概率补报”存在冲突。

**修改建议**：明确使用 confirmed uplink、模组状态、应用层 ACK 中的哪一层作为成功判据；定义补报探测时机和告警路径对重连退避的豁免规则。

### P2-3 资源余量偏紧

当前 map 显示：

- ROM 约 53.84 KB / 64 KB
- RW + ZI 约 7.12 KB / 8 KB

余量不足以随意引入 float FIFO 数组、CMSIS-DSP 大库或多层队列抽象。设计中提到 `arm_sqrt_q15`，但工程未确认引入 CMSIS-DSP 依赖后的体积影响。

**修改建议**：使用原始 FIFO 缓冲和小型整数开方；在实现计划中为每个阶段设置 map 体积红线，超线即优化，而不是等到最后统一处理。

### P2-4 恢复出厂设置未清理新增 ACC 配置

现有 `FLASH_Reset_Param()` 只恢复运行周期配置。新增 ACC 配置后，若恢复出厂逻辑不同步清理或恢复默认 ACC 参数，会导致客户现场调参状态残留。

**修改建议**：恢复出厂设置必须同时恢复 ACC 采样、量程、阈值、告警和 Class 配置默认值，并重启或重新初始化传感器。

## 次要问题

1. `uplink-payload-protocol.md` 和 `acc-sampling-modes-design.md` 被引用但当前仓库中不存在，建议补齐或删除引用。
2. Flash 物理页为 128 B，而当前工程 `FLASH_ONE_PAGE_SIZE` 是 1 KB 逻辑分区步长，文档应说明二者关系，避免实现者混淆。
3. 低功耗模式下 `120 ms` 软件防抖在 1 Hz 时无法验证，应明确低功耗模式先由硬件运动事件唤醒并升频，软件防抖只在高频采样阶段生效。
4. `50 Hz` 临时诊断模式需要定义退出条件、最长持续时间和异常重启后的恢复策略。
5. 告警峰值使用原始合成幅值时，需在平台上与动态运动强度明确区分，避免把 `1.75g` 原始峰值误解为 `750 mg` 动态阈值。

## 建议实施顺序

1. 修订 V1.3，闭环采样配置字段、INT1 语义、HPF/FIFO 前置条件、时间边界和累加器溢出。
2. 做两个前置 POC：LIS3DH 中断/FIFO 批处理时序；模组睡眠唤醒后会话保持与 Class 切换耗时。
3. 在主机端完成算法单测，包括合成幅值、活动分类、防抖、快照边界、覆盖率、溢出和时间跨零。
4. 修复 LIS3DH 驱动：返回值、读回验证、FIFO stream、原始数据批量读取。
5. 实现异步 LoRa/Class C 状态机和告警队列。
6. 最后接协议配置、Flash 持久化、恢复出厂和平台联调。
7. 每阶段检查 RAM/ROM map，并记录批处理最大耗时和 FIFO overrun 计数。
