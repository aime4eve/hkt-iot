- 合并来源：

## 总体结论

方案的总体方向正确：在固件内做本地在线统计，上报平均原始合成幅值、最大原始合成幅值、活动百分比和采样覆盖率，配合独立事件告警，不保存完整原始波形，符合客户已确认需求。快照机制、按持续时间防抖、告警优先级、覆盖率上报和配置持久化思路均值得保留。

但 **V1.2 不建议直接作为开工基线**。合并三份评审后，主要风险不在合成幅值公式或 25 Hz 数据处理量，而在四类工程边界：

1. 低功耗双采样率和硬件唤醒语义未形成可实现协议。
2. 原始幅值统计与当前 LIS3DH HPF 关闭要求、FIFO 批读和驱动返回值处理不匹配。
3. 异步化范围不足，ACK 上行、Class C AT 切换和 I2C 访问仍可能阻塞主循环。
4. 长窗口、动态变速、毫秒计时跨零、网络恢复和功耗口径缺少可验证边界。

建议先修订为 V1.3，完成协议定稿和前置 POC，再进入实现。

## 评审冲突的合并口径

### 1. Stop 前是否关闭 LIS3DH

第一轮评审的“Stop 前 power down LIS3DH 属实”表述不准确。最终口径以第二轮修正为准：

- `control_center.c` 中的 power down 只在 `!device_t.powerState` 的关机/待机分支执行。
- 开机态进入 Stop 的路径不会主动关闭 LIS3DH。
- 更关键的是，当前入网状态下固件本来就不进入 Stop；只有未入网且空闲时才满足 Stop 条件。

因此，设计文档需要区分“当前行为”和“新设计目标”。如果新连续统计模式继续沿用“入网后 MCU 常醒”，则不存在每秒 FIFO 浅唤醒问题，但功耗估算必须按该口径实测。如果新设计希望入网后也进入 Stop，则必须补充浅唤醒路径和唤醒电荷实测。

### 2. `magnitude_sum_mg` 是否溢出

两轮结论并不矛盾，应合并为边界结论：

- 默认 `25 Hz + 10 min` 窗口下，按三轴同时饱和的合成幅值上限约 `13856 mg` 计算，累加值约 `2.08 * 10^8`，`uint32_t` 足够。
- 现有运行配置允许上报周期最大 `1440 min`。在 `25 Hz + 1440 min` 场景下，仅按单轴满量程 `8000 mg` 计算累加约 `1.73 * 10^10`；按三轴合成上限 `13856 mg` 计算约 `3.0 * 10^10`。二者均超出 32 位无符号数上限 `4.295 * 10^9`。

因此设计不能只按默认窗口证明安全，必须为协议允许的最大窗口给出容量证明和实现策略。

## 已确认可行的部分

| 检查项 | 结论 | 依据与限制 |
|---|---|---|
| 25 Hz 统计计算负载 | 可行 | MCU 运行在约 `1.048 MHz MSI`，25 Hz 批处理负载预计为百分之几量级；仍需实测最大批处理耗时 |
| `0xB0~0xB4` 类型值 | 空闲 | 现有协议枚举使用到 `0xA8` 和 `0xFF`，未占用 `0xB0~0xB4` |
| 平均、最大、活动百分比算法 | 可行 | 前提是关闭 HPF、使用原始 X/Y/Z、按有效样本分母计算 |
| 默认窗口累加容量 | 可行 | `25 Hz + 10 min` 下 `uint32_t` 足够；最大窗口仍需改造 |
| `uint16_t` 幅值字段 | 可行 | `±8g` 单轴满量程为 `8000 mg`；三轴同时饱和的合成幅值上限约 `13856 mg`，仍小于 `65535` |
| Flash 容量 | 足够 | 用户区尾部约 2 KB 空闲；但物理页和逻辑分区尺寸需澄清 |
| Class A/C 切换能力 | 具备前提 | 模组已有 `AT+CLASS`；但现有调用是阻塞式，必须异步化 |
| 确认帧能力 | 具备前提 | 已有 `AT+CONFIRM` 相关能力；发送成功判据仍需落到模组返回或应用层 ACK |
| 快照与告警优先级 | 设计正确 | 周期快照不可变，告警优先于周期摘要 |
| 按持续时间防抖 | 高频采样下设计正确 | 1 Hz 低功耗模式下软件防抖无法验证，需硬件唤醒后升频再判定 |

## P0：实现前必须修订

### P0-1 低功耗双采样率无法通过当前协议配置

设计允许：

- 低功耗稀疏采样率：`1/10 Hz`，默认 `1 Hz`
- 运动后高频采样率：`10/25/50 Hz`，默认 `25 Hz`

但 `0xB2`、`0xB3` 和 Flash 结构中只有一个 `sampling_rate_hz` 字段，无法同时保存两个采样率。配置表、下行协议、上报协议和持久化结构彼此不一致。

**修订要求**：

1. 拆分为 `low_power_sampling_rate_hz` 与 `active_sampling_rate_hz`。
2. 同步修改 `0xB2`、`0xB3`、Flash 结构、默认值、校验规则和平台解码器。
3. 明确连续模式使用哪个字段，避免三种模式语义混用。

### P0-2 低功耗硬件唤醒与告警判定链路未定义

设计只写“启用 LIS3DH 硬件运动中断”，但缺少可实现细节：

1. 硬件唤醒阈值、持续时间、锁存和 AOI 组合逻辑。
2. FIFO watermark 与运动事件同时路由到 INT1 时的区分方式。
3. 1 Hz 模式下 FIFO watermark 配置。若仍为 25 级，MCU 约 25 秒才处理一次，无法满足运动后升频时效。
4. 硬件中断阈值与 `750 mg` 软件告警阈值的关系。
5. 1 Hz 下 `120 ms` 软件防抖退化为单点判定，测试用例无法验证。

**修订要求**：

- 定义硬件事件仅用于唤醒和切换到高频采样；正式告警必须在高频连续采样后由软件阈值和持续时间防抖确认。
- 在协议中增加硬件唤醒阈值和持续时间字段，或明确它们由活动/告警阈值推导且不可独立配置。
- 明确 INT1/INT2 路由和中断源识别方法。
- 说明 1 Hz 稀疏采样不承诺捕捉短促冲击，只用于活动趋势和唤醒。

### P0-3 原始幅值统计的传感器前置条件不成立

设计要求静止合成幅值接近 `1g`，但当前活动路径启用了 LIS3DH 高通滤波。若继续开启 HPF，静止合成幅值趋近 0，`abs(magnitude - 1g)` 活动分类将失效。

同时，当前驱动实现与设计目标存在需要闭环的工程落差：

1. `lis3dh_get_raw_data_fifo()` 逐样本读取 6 字节，不是一次寄存器地址自动递增批量读。
2. 设计未明确选择 stream 还是 collect 模式。collect 模式在 overrun 后清 FIFO 重建的方案并非错误；stream 模式更适合连续统计中持续保留新样本，但需评估 overrun 前后新旧样本交织对窗口统计的影响。
3. `lis3dh_set_mode()` 写入后固定返回 `false`，会导致配置失败回滚逻辑全部误判失败。
4. `lis3dh_set_scale()` 未做完整读回验证，不满足配置失败保持旧配置的要求。

**修订要求**：

- 连续统计模式必须关闭 HPF，使用未滤波原始 X/Y/Z。
- 明确 FIFO 模式选择、watermark、overrun 恢复流程和批量读方式；若选择 stream 模式，需说明 overrun 前后样本语义。
- 驱动先修复返回值、超时、读回验证和原始批量读，再接入配置协议。

### P0-4 异步化范围不完整

设计第 7 章要求改造 `sendLoRaWANData()`，实际函数位于 `USER/Drive/communicate.c`；第 12 章又将异步发送改动列在 `Compents/LoRa/LoRaWAN_APPLY.c`，改动归属需要修正。更关键的是，阻塞路径不止一处：

1. 周期上行 `sendLoRaWANData()` 存在 Busy 无超时死等。
2. 平台 ACK 上行路径复制了同样的阻塞逻辑。
3. 告警成功后的 `AT_LoRaWAN_setClass()` 最坏可阻塞约 7.5 秒。
4. 现有 I2C 读写存在无超时死等轮询，传感器异常会卡死主循环。

25 Hz 下 FIFO 32 级约 1.28 秒充满；watermark 25 级触发后，只剩约 `(32-25)/25 = 280 ms` 处理余量。任何秒级阻塞都会造成 overrun。

**修订要求**：

- LoRa 数据发送、ACK 发送、Class C 打开、Class 读回、窗口计时和恢复 Class A 全部纳入同一异步状态机。
- I2C 寄存器读写增加超时和失败计数。
- 将 280 ms 硬时限写入第 5.4 节验收标准，与“调度周期不高于 800 ms”统一。

### P0-5 协议仍有未决项，不能进入“协议定稿”步骤

实施顺序第 1 步是协议定稿，但当前至少存在以下未决项：

1. `0xB3` 返回帧是去掉 `Flags`，还是复用完整 `0xB2` 格式。
2. `0xB2` 的 persist/temporary 两位都为 0 时的默认语义。
3. `0xB1` 延迟补报缺少事件发生时间。
4. 双采样率字段缺失。
5. 硬件唤醒参数是否可配置。

**修订要求**：

- 在 V1.3 中逐项定死，不再保留“实现阶段二选一”。
- `0xB1` 增加事件 UTC 时间戳或相对当前上行的分钟偏移，并定义时间未同步时的无效值。
- 平台和设备同步更新解码器与验收样例。

## P1：开工前需闭环的高风险项

### P1-1 运行/睡眠架构与功耗口径未定

当前入网态固件不进入 Stop，已有 `10 min @ 2.2 mA` 基线更接近 MCU 常醒口径。新设计若保持该架构，需实测连续 ACC 常开后的增量；若改为入网后 Stop + FIFO 唤醒，则必须设计浅唤醒路径。

浅唤醒路径不能沿用当前 Stop 后全量重初始化时钟、UART、I2C 的流程，否则每秒一次 FIFO 唤醒的电荷开销会显著影响功耗。设计需按唤醒源区分：

- RTC 周期唤醒
- ACC FIFO 唤醒
- 告警事件唤醒
- 按键或外部事件唤醒

ACC FIFO 唤醒应只读 FIFO、更新统计并快速回睡，不应触发 GPS、LoRa 和串口全量重建。

### P1-2 长窗口累加器溢出

见“评审冲突的合并口径”。设计必须采用以下方案之一：

1. 使用 64 位累加器。
2. 使用 48 位压缩累加。
3. 按窗口分段求均值。
4. 限制“采样率 × 量程 × 窗口时长”组合，拒绝会溢出的配置。

推荐直接使用 64 位累加器，RAM 增量极小，并能把协议最大窗口纳入安全范围。

### P1-3 动态覆盖率与毫秒计时边界未闭环

低功耗模式在 `1 Hz` 与 `25 Hz` 间切换时，`expected_samples` 必须按每段时长和当前 ODR 分段累加，不能用窗口结束时的当前采样率反推。

当前 `get_syspant_ms()` 在超过 `86400000` 后清零。防抖、静默期、窗口到期和超时若直接比较时间戳，会在跨零点时出错。

**修订要求**：

- 提供单调毫秒计数或安全的时间差函数。
- 采样率切换时立即结算并累加 `expected_samples`。
- 测试计划增加时间跨零、变速窗口、窗口边界快照和 FIFO overrun 后覆盖率用例。

### P1-4 LoRaWAN 会话保存缺少模组行为验证

设计要求 Stop 前保存会话，唤醒后仅确认丢失才重连，但当前代码会在 Stop 相关路径清除 `joinState`，且未定义如何确认模组睡眠后仍保留会话。

**前置 POC 要求**：

1. 模组睡眠后唤醒是否会话仍有效。
2. 读取网络/入网/Class 状态的可靠命令。
3. 命令模式与透传模式切换耗时。
4. 会话丢失时的判定和回退路径。

### P1-5 Class C 功耗表计算错误

第 11 章常驻 Class C 的寿命估算有 3~4 倍偏差。按基线约 `2.4 mA` 加上额外 `4~15 mA`，总平均电流为 `6.4~17.4 mA`：

- 按 80% 有效容量：约 `2.4~6.5` 个月
- 按 70% 有效容量：约 `2.1~5.7` 个月

不是文档中的 `12~28` 个月。虽然常驻 Class C 不纳入默认验收，但该数字会误导平台和运维决策，必须修正。

同时，`4~15 mA` 范围过宽，应先查模组规格书并实测告警后 5 分钟 Class C 窗口的实际电流。

### P1-6 “发送成功”和“网络恢复”缺少可验证判据

当前状态脚可能仅表示模组完成发送流程，不必然等价于 LoRaWAN confirmed uplink 收到 ACK，也不等价于平台应用层收到事件。

现有连续失败后的 30 分钟重连退避，与“5 分钟内高概率补报”在网络抖动场景下冲突。

**修订要求**：

1. 明确成功判据：confirmed uplink、模组状态、平台应用层 ACK，或组合条件。
2. 明确告警补报触发点：周期上行成功后、定时探测、退避到期，或独立告警重试。
3. 说明告警路径是否豁免 30 分钟重连退避。
4. 定义补报最大次数、丢弃策略和计数上报。

### P1-7 资源余量偏紧

当前 map 显示：

- ROM 约 `53.84 KB / 64 KB`
- RW + ZI 约 `7.12 KB / 8 KB`

余量不足以随意引入 float FIFO 数组、CMSIS-DSP 大库、复杂队列抽象或大量调试字符串。`arm_sqrt_q15` 依赖的代码体积尚未验证。

**修订要求**：

- 使用原始 FIFO 缓冲和小型整数开方。
- 每个实现阶段记录 map 体积，设置 RAM/ROM 红线。
- 删除或压缩实时路径中的 float 格式化日志，避免体积和执行时间回退。

### P1-8 恢复出厂设置未覆盖新增配置

现有恢复出厂逻辑只恢复运行周期等配置。新增 ACC 配置后，若不同步处理，会残留现场阈值、采样率、量程、告警和 Class C 窗口调参状态。

**修订要求**：恢复出厂设置必须恢复 ACC 采样、量程、阈值、告警、Class 配置默认值，并重新初始化传感器和模组配置。

### P1-9 引用协议文档缺失

第 1 章引用的 `Docs/uplink-payload-protocol.md` 和 `Docs/acc-sampling-modes-design.md` 在当前仓库中不存在。平台联调时缺少权威协议口径。

**修订要求**：补齐文档，或移除引用并明确本设计就是唯一协议基线。

## P2：实现期注意项

1. **Flash 物理页与逻辑分区混淆**：STM32L0 物理擦除页为 128 B；工程宏 `FLASH_ONE_PAGE_SIZE = 0x400` 是 1 KB 逻辑分区步长。新配置区应明确物理地址、擦除范围和是否与旧逻辑分区互相影响。
2. **建议评估 EEPROM**：STM32L051C8 自带 2 KB EEPROM，字节可写且寿命更高。Flash 方案可用，但 EEPROM 可能更简单可靠；V1.3 应明确选型理由。
3. **新增分区位置**：建议放在用户区首页或尾部空闲区，并确认擦写不影响既有参数。
4. **ACK 错误码是新能力**：现有 ACK 只有 `0xFF` 成功样式，8.6 的错误码表不是“沿用现有机制”，平台侧需要同步开发。
5. **50 Hz 临时诊断模式**：需定义最长持续时间、退出条件、重启后恢复策略和功耗不计入验收的边界。
6. **幅值语义需平台提示**：告警峰值是原始合成幅值，动态阈值是 `abs(magnitude - 1g)`；平台不能把 `1.75g` 原始峰值误解为超过 `750 mg` 动态阈值的同一量纲。
7. **量化精度**：`±4g` 高分辨率下 LSB 约 `1.95 mg`，`±8g` 约 `3.9 mg`；协议整数 mg 上报可行，但不能承诺 1 mg 精度。
8. **源文档单位笔误**：`1_5_10分钟功耗寿命预估.txt` 将平均电流写成 mAh，设计引用时已用 mA，源文件建议修正。

## 前置 POC 清单

在协议定稿和编码之间，建议完成四个 POC，并把结果写回 V1.3：

1. **模组会话 POC**：睡眠、唤醒、会话保持、状态查询、模式切换和 Class 切换耗时。
2. **ACC 批处理 POC**：1.048 MHz 主频下，25 Hz、watermark 20/25、I2C 批读、整数开方和统计更新的最大耗时；验证 280 ms 余量和 60 秒零 overrun。
3. **睡眠架构 POC**：入网后 MCU 常醒与 Stop 浅唤醒两种方案的实测平均电流，确认第 11 章功耗口径。
4. **Class C 电流 POC**：告警成功后 5 分钟窗口的实耗电流，修正告警频繁场景寿命模型。

## 修订后的实施顺序

1. 修订 V1.3，定稿协议字段和所有未决语义。
2. 完成 LoRaWAN 模组会话与 Class 切换 POC。
3. 完成 LIS3DH FIFO/中断/批处理 POC。
4. 主机端算法单测：合成幅值、活动分类、防抖、快照边界、动态覆盖率、累加溢出、时间跨零。
5. 修复 LIS3DH 驱动：返回值、读回验证、超时、FIFO 模式选型、原始批量读。
6. 实现异步 LoRa/ACK/Class 状态机和告警队列。
